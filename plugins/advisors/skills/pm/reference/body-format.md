# PM 고문 리포트 본문 양식

리포트 머리와 공통 항목은 `shared/report-base.md` 를 따른다. 아래는 "본문" 자리에 넣는 모드별 양식이다. 모든 수치 옆에 계산 명령이나 출처를 붙인다.

## next — 다음 작업

```markdown
### 오늘 쓸 수 있는 시간
<값> — 출처(사용자 / 프로필 pm.capacity / pm.capacity_file)

### 후보
| 종류 | 후보 | 왜 지금인가 | 규모 | 근거 |
|---|---|---|---|---|
| 이슈 | #N 제목 | 순서 1위, 필수 | M | pm_calc issues 출력 |
| 때가 된 점검 | PC-002 성능 주기 점검 | 지남 3일 | - | pm_calc cadence |
| 위험 결정 | PR-003 | 결정 시점 2일 남음 | - | pm_calc risks |
| 부채 결정 | TD-B-004 | 결정 시점 지남 1일, td 권고 "갚음 — 다음 마일스톤" | - | pm_calc debts |
| 회고·계획 | 주간 점검 | 마지막 주간 점검 8일 전 | - | |

### 추천
- 추천: <하나>. 이유 한두 줄.
- 대안: <하나>. 추천하지 않은 이유.
- 넘길 곳: 이슈 작업이면 프로필 `pm.next_task_entry`(범위·오늘 조각 결정), 고문 점검이면 그 고문 명령.
```

이슈 순서는 `pm_calc.py issues` 의 라벨 기준 초안이다. 선행 관계까지 반영한 순서와 오늘 조각은 `pm.next_task_entry` 스킬의 결과를 따른다고 적는다.

## scope — 범위 판단

```markdown
### 대상
한 문장. 무엇을 더하거나(빼거나, 미루거나) 하려는가.

### 일정 관점 판단
| 질문 | 답 | 근거 |
|---|---|---|
| 필수성 | A / B / C | 마일스톤 완료 기준 MC-... |
| 규모 | S / M / L / 모름(시간 상자 제안) | |
| 넣으면 필수 비율 | x% → y% | pm_calc capacity |
| 밀려나는 일 | | |
| 새로 생기는 위험 | | |
| 늦게 하면 생기는 비용 | | |

### 제안
지금 넣기 / 다음 마일스톤 통 / 백로그 / 넣지 않기 가운데 하나와 조건.

### 기획 판단이 필요한 부분
원칙·재미 판단은 design 고문 몫이다. 질문함에 올린 질문 ID.

### 기술 판단이 필요한 부분
구현 가능성·구조 판단은 td 고문 몫이다. 질문함에 올린 질문 ID. 없으면 "없음".
```

## playtest — 플레이테스트 계획

```markdown
### 이번 테스트로 확인할 것
예·아니오 점검 항목 3~7개 (methods.md 7-4). 지난 테스트 항목 가운데 다시 볼 것 포함.

### 대상과 진행
- 대상: 누가, 몇 명, 처음 보는 사람인가
- 빌드·기기 준비 점검: 설치, 직접 몇 번 해 봄, 막아 둘 고장 부분
- 안내 문장: 한두 문장
- 시간: 분
- 관찰 기록지 칸: 시각 / 장면 / 한 일 / 막힘 / 말한 것

### 끝난 뒤 문장 (동의 척도)
이 게임이 필러로 노리는 경험만. 장면 이름을 넣은 문장.

### 결과를 받을 곳
기록 파일 위치(프로필 design.playtest_records). 결과가 들어오면 design 고문에 해석을, 다음 주간 점검에 일정 반영을 넘긴다.
```
