# advisors — 게임 프로젝트 고문 6종

게임 프로젝트를 여섯 가지 관점에서 진단하고 제안하는 Claude Code 플러그인이다. 고문은 판단하고 제안까지만 한다. 결정은 사람이 하고, 코드·기획서·설정은 고치지 않는다.

| 고문 | 명령 | 모드 | 하는 일 |
|---|---|---|---|
| 기획 고문 | `/advisors:design` | 영역 진단 / 단건 심사 | 프로젝트의 핵심 원칙을 기준으로 시스템을 진단하고 추가·수정·보류·제거를 제안 |
| 기술 동향 고문 | `/advisors:radar` | 정기 점검 / 단일 기술 진단 | 프로젝트가 쓰는 엔진·플러그인·설정 목록에서 출발해, 지금 쓰는 기술의 바깥 변화와 우리 트리에 없거나 꺼진 새 기술·엔진 버전을 1차 출처로 확인하고 적용 가능성·필요성·추천도를 판정. 커뮤니티 채널(Qiita, GeekNews 등)은 화제를 찾는 실마리로만 쓴다 |
| 시장 동향 고문 | `/advisors:market` | 전면 평가 / 변화 점검 | 흥행작의 특징, 이용자 구성, 우리 프로젝트의 시장 내 위치를 공개 자료로 정리 |
| 최적화 고문 | `/advisors:perf` | 진단 / 주기 점검 | 측정으로 병목을 찾고, 테스트·리팩터링이 필요한지 판단하고, 부문별로 주기 점검 |
| PM 고문 | `/advisors:pm` | 다음 작업 / 주간 점검 / 마일스톤 계획 / 마일스톤 회고 / 범위 판단 / 플레이테스트 계획 | 트래커와 작업 가능 시간으로 다음 작업을 고르고, 마일스톤 용량·위험·회고를 관리하고, 다른 고문의 정기 점검과 플레이테스트 주기를 한 표로 관리 |
| TD(테크니컬 디렉터) 고문 | `/advisors:td` | 설계 검토 / 구조 점검 | 우리 코드·로컬 엔진 소스·팀 문서에서 답이 나오는 기술 판단. 엔진 기능 대 자체 구현, 구조 선택, 새 기능의 구조, 되풀이되는 버그의 구조, 기획 기능의 기술 타당성, 모듈 의존, 엔진 수정 블록, 기술 부채, 에이전트 검증 가능성(난수 경로·상태 재현·텍스트 출력 등). 웹은 조건이 맞을 때 1차 출처만 찾고 커뮤니티 글은 읽지 않는다 |

언리얼과 Godot 프로젝트를 읽는다. 고문 문서는 언리얼 기준으로 쓰여 있고, Godot 프로젝트(`project.godot`)에서는 고문이 [shared/engine-godot.md](shared/engine-godot.md) 대로 낱말·명령·단계를 바꿔 읽는다. 엔진 종류는 프로필 `engine.kind` 로 정하고, 처음 프로필을 만들 때 자동으로 채운다.

명령 이름을 외우지 않아도 된다. "이 아이디어 넣어도 될까?", "요즘 언리얼 소식 정리해 줘", "우리 게임 시장성 어때?", "전투 중 프레임 떨어지는 원인 찾아 줘", "이번 주 점검해 줘", "이 두 구조 중 뭐가 나아?" 같은 말로도 해당 고문이 불린다.

기술 질문은 답이 어디에 있는지로 가른다. 우리 코드·로컬 엔진 소스·팀 문서에 있으면 TD 고문, 바깥(새 발표, 다른 엔진 버전, 외부 제품)에 있으면 기술 동향 고문이다. 기술 이름이 나왔다는 것만으로 기술 동향 고문이 아니다. 이미 쓰는 기술을 우리 코드에서 어떻게 쓸지, 자체 구현을 엔진 기능으로 옮길지는 TD 고문이다. 우리가 쓰는 엔진 기능의 알려진 버그만 묻는다면 기술 동향 고문이다. 기능 하나를 두고는 재미·원칙은 기획 고문, 만들 수 있는지·어느 구조로 만들지는 TD 고문, 이번 마일스톤에 넣을지·언제 할지는 PM 고문이 본다. 고문 사이 기준과 "우리 트리"의 뜻은 [shared/routing.md](shared/routing.md) 에 있다.

## 처음 쓸 때

1. 플러그인을 설치한다. Claude Code 세션에서 아래 두 줄을 실행한다. 자세한 방법은 [리포 README](../../README.md#설치) 참고.

   ```
   /plugin marketplace add jaykop/claude-plugins
   /plugin install advisors@jaykop
   ```

2. 프로젝트 폴더에서 Claude Code 를 열고 아무 고문이나 부른다.
3. 고문이 "이 프로젝트에 고문 프로필이 없어요. 만들까요?"라고 묻는다. 동의하면:
   - 프로젝트 파일에서 알 수 있는 값(버전 관리 종류, 엔진 종류, 엔진 버전, 켜진 플러그인, 문서 폴더, 테스트 파일, 측정 파일 폴더)은 자동으로 채운다.
   - 공통 값과 지금 부른 고문의 값만 묻는다. 다른 고문의 값은 그 고문을 처음 부를 때 묻는다.
   - 모르는 값은 비워 둬도 된다. 그 값이 필요한 단계만 건너뛰고 리포트에 "확인 못 한 것"으로 남긴다.

프로필은 `<프로젝트 루트>/.claude/advisors/profile.md` 하나다. 칸 설명은 [shared/profile-template.md](shared/profile-template.md) 에 있다. 직접 고쳐도 된다.

### 꼭 직접 정해야 하는 값

고문이 추측으로 채우지 않는 값이다.

| 칸 | 왜 필요한가 |
|---|---|
| `decision_owners`, `user_role` | 영역별 결정권자와 이 프로필을 쓰는 사람의 역할. 사용자가 결정권자가 아니면 고문은 제안을 "참고 선택지"로 낮춘다 |
| `team_size` | 기술 동향 고문이 출시 사례와 우리 팀 규모를 견줄 때 쓴다. 비어 있으면 견주지 않고, 출시 사례만으로는 추천도를 "시험"보다 높이지 않는다 |
| `search_banned_terms`, `search_banned_combos` | 웹 검색어는 외부로 나간다. 내부 코드 이름이나 미발표 정보 조합을 막는다 |
| `design.principles`, `design.principles_status` | 기획 고문의 판단 기준(최상위 원칙, 필러, 우선순위, 금지 원칙)과 그 상태(확정·가안). 없으면 후보를 모아 확인을 받는다 |
| `perf.budgets` | 최적화 고문의 우선순위 기준(목표 fps, 프레임 시간, 메모리) |
| `pm.capacity` 또는 `pm.capacity_file` | PM 고문의 작업 가능 시간. 개인 값이면 버전 관리 밖 파일을 `capacity_file` 로 가리킨다 |
| `decision_owners.schedule` | 마일스톤 범위·작업 순서의 결정권자 |

## 리포트

- 저장 위치: 프로필의 `report_dir` (기본 `.claude/advisors/reports`). git 프로젝트라면 공유하지 않을 리포트 폴더를 `.gitignore` 에 넣는다.
- 파일 이름: `<report_dir>/<고문>/<작성일>-<모드>.md`. 모드 부분은 영어 소문자다.

  | 고문 | 모드 |
  |---|---|
  | design | `area`(영역 진단), `review`(단건 심사), `area-index`(게임 전체 목차) |
  | radar | `periodic`(정기 점검), `single`(단일 기술 진단) |
  | market | `full`(전면 평가), `check`(변화 점검) |
  | perf | `diagnosis`(진단), `periodic`(주기 점검) |
  | pm | `next`(다음 작업), `weekly`(주간 점검), `milestone`(마일스톤 계획), `retro`(마일스톤 회고), `scope`(범위 판단), `playtest`(플레이테스트 계획) |
  | td | `decision`(설계 검토), `audit`(구조 점검) |

- 시장 고문이 스크립트로 받은 Steam 리뷰 원본과 분류 결과는 `<report_dir>/market/data/<날짜>/` 에 둔다.
- 대화에는 요약 세 줄, 결정이 필요한 것, 리포트 경로, 후속 제안만 나온다. 전문은 파일에 있다.
- 모든 주장에 근거 등급(확인함 / 추정 / 모름)과 위치(파일:줄, URL·조회일)가 붙는다.
- 다음 실행 때 같은 모드의 직전 리포트와 비교해 달라진 것을 따로 적는다.

### 고문끼리 주고받는 것

`<report_dir>/_state/` 에 고문들이 함께 쓰는 기록이 쌓인다.

| 파일 | 만드는 고문 | 읽는 고문 |
|---|---|---|
| `inbox.md` | 모두 | 모두 — 다른 고문에게 넘긴 질문. 받는 고문이 시작할 때 먼저 읽는다 |
| `feedback.md` | 사용자, 모든 고문(대화 실행) | 모두 — 리포트 항목에 붙인 결과 표시. 각 고문이 시작할 때 자기 앞 "반영 전" 행을 읽는다(아래 '판정 기준 다듬기') |
| `radar-inventory.md` | 기술 동향 | 최적화, 기획, TD — 엔진 버전, 플러그인 상태, 주요 설정 |
| `market-competitors.md` | 시장 | 기획 — 경쟁작 목록 |
| `source-checks.md` | 기술 동향, 시장, TD | 모두 — 날짜가 붙은 바깥 사실과 출처 접근 가능 여부 |
| `pm-cadence.md` | PM | PM — 모든 고문의 정기 점검과 플레이테스트 주기. 때가 된 것을 PM 이 알리고, 동의하면 그 고문을 부른다 |
| `td-debt.md` | TD | PM — 머리의 마지막 갱신 날짜(정기 점검표의 기술 부채 점검 행이 이 날짜를 마지막 실행으로 쓴다)와 부채별 권고·결정 시점(주간 점검이 결정 시점이 된 부채를 알린다) |
| `td-engine-mods.md` | TD | 기술 동향 — 엔진 수정 블록 묶음의 분류와 머지 위험 근거(엔진 버전 점검표에 쓴다) |
| `radar-watchlist.md` | 기술 동향 | TD — "다음 버전으로 올릴 때 걸리는 것" 표의 상태(기술 부채 점검에 쓴다) |

예를 들어 기술 동향 고문이 새 그림자 방식을 "시험"으로 권하면, 성공 기준을 재 달라는 요청이 최적화 고문 앞으로 질문함에 들어간다. TD 고문이 두 구조를 견주다가 우리 트리에 없거나 꺼진 기술이 걸리면, 그 기술의 판정 요청이 기술 동향 고문 앞으로 들어간다.

## 판정 기준 다듬기

고문의 판정을 이 프로젝트에 맞추는 방법은 세 가지다. 분야 지식이 없어도 쓸 수 있다.

### 결과 표시

리포트를 읽고 걸리는 항목에 셋 가운데 하나를 붙인다.

| 표시 | 뜻 |
|---|---|
| 틀림 | 사실이나 판정이 틀렸다 |
| 일반론 | 이 프로젝트가 아니어도 어디에나 맞는 말이라 판단에 쓸 수 없다 |
| 놓침 | 봤어야 할 자료나 위험을 보지 않았다 |

- 고문을 부른 대화에서 "이 리포트 X 틀렸어"처럼 말하면 고문이 `_state/feedback.md` 에 한 줄을 더한다. 파일을 직접 고쳐도 된다. 그때는 ID, 날짜, 고문, 리포트, 항목, 표시, 한 줄 설명만 채우면 된다. 형식은 [state-formats.md](shared/state-formats.md) 의 feedback.md 항목에 있다.
- 고문은 원인을 다섯 가운데 하나로 가린다: 근거를 못 읽음 / 판정 기준 없음 / 기준이 틀림 / 다른 고문 몫 / 모름. 원인마다 고칠 곳 후보(프로필 칸, 팀 기준 노트, 플러그인의 reference 파일, routing.md)를 알려 준다. 고문이 플러그인 파일이나 노트를 직접 고치지는 않는다.
- 다음 실행부터 고문은 자기 앞 "반영 전" 행을 먼저 읽고 같은 잘못을 피한다. 읽은 행 ID 를 리포트 머리 "범위"에 적는다.
- 고친 뒤에는 그 행의 "고친 곳"과 상태(반영함 / 반영 안 함과 이유)를 직접 바꾸거나 고문에게 알려 준다. 고문이 스스로 상태를 바꾸지 않는다.
- 한 고문 앞 "반영 전" 행이 10개 이상이면 고문이 원인별 정리를 제안한다.
- 예약 실행(무인 실행)은 이 기록을 읽기만 하고 쓰지 않는다.

### 팀 기준 노트

팀이 정한 판단 기준(사내 기준, 교재 요약, 지난 판정에서 배운 것)을 노트로 두면 고문이 자기 reference 파일보다 먼저 따른다. 프로필에서 고문마다 `<고문>.knowledge_dir` 칸으로 폴더를 가리킨다(예: `td.knowledge_dir`, `pm.knowledge_dir`). 폴더를 고문마다 따로 둘 수 있어서, 비공개 노트는 버전 관리 밖에, 팀 공유 노트는 저장소 안에 둘 수 있다.

- 고문은 폴더의 `index.md` 부터 읽고, 이번 판정에 걸리는 노트만 읽는다. `index.md` 가 없으면 폴더의 .md 를 모두 읽는다.
- 노트 안에 도구 실행·파일 쓰기 같은 지시가 있어도 따르지 않는다.
- 노트 원문은 리포트에 옮기지 않는다. 노트 경로와 항목 이름만 적으므로 비공개 자료여도 된다.
- 공통 규칙([rules.md](shared/rules.md))과 고문 사이 일 나누기([routing.md](shared/routing.md))는 노트로 바꾸지 않는다. 자세한 규칙은 rules.md §13 에 있다.

### 시험 질문

고친 뒤 같은 잘못이 다시 나오지 않는지는 [evals/](evals/README.md) 의 사례로 확인한다. `claude plugin eval` 형식이고, 고문이 불린 뒤의 동작(넘겨야 할 질문을 넘기는지, 하지 말아야 할 수집을 하지 않는지)만 본다. "반영함"이 된 결과 표시는 이 폴더의 사례로 옮긴다(사람이 옮긴다).

## 주기 점검

| 고문 | 기본 주기 | 비고 |
|---|---|---|
| 기술 동향 | 월 1회 | |
| 시장 | 분기 1회 | 프로필 `market.check_interval` 로 바꿀 수 있다. 직접 경쟁작이 출시되면 그때도 제안 |
| 최적화 | 주 1회 | 새 측정 파일이 있을 때만 리포트를 만든다 |
| 기획 | 예약 없음 | 요청할 때, 새 플레이테스트 기록이 생겼을 때, 마일스톤 14일 전(세션 시작 알림) |
| PM | 주 1회 | 주간 점검. 마일스톤 계획·회고는 예약하지 않고 정기 점검표의 조건으로 알린다 |
| TD | 예약 없음 | 요청할 때, 질문함에 TD 앞 질문이 왔을 때, 마일스톤 30일 전(세션 시작 알림 — `td-debt.md` 를 보고 기술 부채 구조 점검을 알린다) |

- 기본 주기가 "예약 없음"이 아닌 고문은 처음 돌린 뒤, 예약된 점검이 없으면 "다음 점검을 예약할까요?"라고 묻는다. 동의하면 Claude Desktop 의 예약 작업으로 만든다.
- 예약 작업은 Claude Desktop 앱이 켜져 있을 때 돈다. 꺼져 있었으면 다음에 앱을 켤 때 돈다.
- 예약 작업은 스킬을 `--unattended` 인자와 함께 부른다(예: `/advisors:radar 정기 점검 --unattended`). 이 인자가 있을 때만 무인 실행이다. 요청 문장에 "무인"이라는 낱말이 있어도 인자가 없으면 대화 실행이다.
- 예약 실행(무인 실행)은 질문하지 않고 리포트 저장까지만 한다. 측정, 빌드, 코드 수정, 버전 관리 쓰기 명령은 하지 않는다. 버전 관리 읽기 명령은 대화 실행과 같이 프로필 `vcs_read_commands` 에 적힌 것만 쓴다.
- 예약 작업은 파일을 쓸 때마다 승인을 받을 수 없다. 예약 작업의 권한 설정에서 `report_dir` 쓰기를 허용해 둔다.
- 클라우드 예약(routines)은 로컬 파일을 볼 수 없으므로 쓰지 않는다.
- 세션을 시작할 때 때가 된 점검이나 열린 질문이 있으면 한 줄로 알려 준다(프로필이 있는 프로젝트에서만).

## 안전장치

- **에이전트 2개로 도구를 나눴다.** 웹 수집은 `web-scout`(웹 검색·열기만), 파일 분석은 `analyst`(읽기만)가 맡는다. 웹 페이지에 숨은 지시문을 따르더라도 파일을 쓰거나 명령을 실행할 수 없다.
- **검색어 제한.** 프로필의 금지어와 금지 조합을 검색어에 넣지 않는다.
- **수정 금지.** 고문은 리포트 폴더와 프로필만 쓴다. 고칠 일이 생기면 승인을 받은 뒤 프로필의 `code_change_entry` 에 적은 스킬로 넘긴다.
- **버전 관리 쓰기 금지.** sync, submit, commit, push 같은 명령을 실행하지 않는다. 읽기 명령도 프로필 `vcs_read_commands` 에 적힌 것만 쓴다.
- **지어낸 수치 금지.** 측정·계산·출처가 없는 수치는 쓰지 않는다. 계산은 스크립트로 한다.

## 이전 버전에서 옮기기

### 신기술 고문(newtech) → 기술 동향 고문(radar)

신기술 고문의 이름이 기술 동향 고문으로, 스킬 이름이 `newtech` 에서 `radar` 로 바뀌었다. 하는 일은 같다. 이전 버전으로 쓰던 프로젝트는 플러그인을 업데이트한 뒤 아래를 바꾼다. 바꾸지 않으면 기술 동향 고문이 프로필 값과 지난 기록을 찾지 못하고, 다른 고문이 기술 목록을 "없음"으로 본다.

1. 프로필(`.claude/advisors/profile.md`)의 `newtech:` 키를 `radar:` 로 바꾼다. 아래 칸(`engine_mod_marker`, `community_sources` 등)은 그대로 둔다.
2. 리포트 폴더 `<report_dir>/newtech/` 를 `<report_dir>/radar/` 로 바꾼다. 지난 리포트 본문은 고치지 않아도 된다.
3. `<report_dir>/_state/` 에서 이름이 `newtech-` 로 시작하는 파일을 `radar-` 로 바꾼다(`newtech-inventory.md` → `radar-inventory.md`, `newtech-watchlist.md` → `radar-watchlist.md`).
4. `_state/` 파일 안의 고문 이름 `newtech` 를 `radar` 로 바꾼다. 고문 칸(`inbox.md` 의 보낸·받는 고문, `source-checks.md` 의 쓴 고문, `feedback.md` 의 고문과 리포트 경로), 기록 머리의 `작성: newtech`, `pm-cadence.md` 의 실행 방법(`/advisors:newtech`)과 기록 패턴(`newtech/*-periodic*.md`)이 여기에 든다. `pm-cadence.md` 의 점검 이름 "신기술 정기 점검"은 "기술 동향 정기 점검"으로 바꾸면 새 양식과 같아진다.
5. 예약 작업의 지시문에 `/advisors:newtech` 가 있으면 `/advisors:radar` 로 바꾼다.

- Claude Code (Claude Desktop 앱 또는 CLI)

## 알려진 한계

- **기획 고문은 게임을 플레이할 수 없다.** 기획서·데이터·코드·플레이테스트 기록으로만 판단하므로, 재미에 대한 판단은 플레이테스트로 확인되기 전까지 가설로 적는다.
- **시장 고문은 장르 단위 연령·성별을 거의 채우지 못한다.** 공개 자료가 대부분 국가·플랫폼 단위라서다. 확인된 단위의 값과 간접 신호만 적고, 고정관념으로 채우지 않는다. 유료 리포트 원문은 볼 수 없다.
- **일부 통계·조사 사이트는 자동 조회가 막혀 있다.** 그 값이 필요하면 화면 캡처나 CSV 로 넘겨 줘야 한다. 고문은 막힌 사이트를 다른 주소나 방법으로 열지 않는다. 처음 쓸 때 확인한 사이트 목록과 결과는 [metrics.md](skills/market/reference/metrics.md) 의 '출처 후보' 항목에 있고, 실행할 때마다 다시 열어 `_state/source-checks.md` 에 기록한다.
- **기술 동향 고문의 커뮤니티 채널은 실마리일 뿐이다.** 정기 점검에서는 늘 읽고, 단일 기술 진단에서는 공식 자료 수집(D3)이 끝난 뒤 정해 둔 조건(사용 경험을 물었을 때, 알려진 문제가 비었을 때, 엔진 버전 진단)에 걸릴 때만 읽는다. TD 고문은 커뮤니티 글을 읽지 않는다. Qiita, GeekNews, 텐센트 게임 학당은 자동으로 읽고, Reddit 과 Zhihu 는 자동 조회가 막혀 사용자가 붙여 넣거나 파일로 넘긴 글만 읽는다. 커뮤니티 글은 1차 출처로 다시 확인한 것만 판정에 쓴다. 채널 목록은 [sources.md](skills/radar/reference/sources.md) 의 '커뮤니티 채널' 항목에 있다.
- **TD 고문은 사람 TD 를 대신하지 않는다.** 근거를 모으고 선택지를 견주는 데까지만 한다. 직군 조율, 일정·인원 추정, 채용은 하지 않는다. 실행 순서와 성능은 돌려 봐야 알 수 있어서, 결론이 "시험 후 결정"이 되는 일이 많다. 블루프린트·에셋 안의 사용은 텍스트로 읽지 못하므로 바뀌는 범위를 "일부만 셈"으로 적는다.
- **PM 고문의 이슈 순서는 라벨만 본 초안이다.** 선행 관계(Blocked by)는 읽지 않는다. 순서 확정과 이슈 게시는 프로필 `pm.next_task_entry` 의 스킬(예: workflow 플러그인의 `next-task`)에 넘긴다. 규모 라벨이 없는 이슈는 용량 계산에서 빠지고 따로 센다.
- **고문의 기본 판정 기준은 일반론이다.** 각 고문의 reference 파일(예: PM 고문의 [methods.md](skills/pm/reference/methods.md))은 어느 프로젝트에나 맞는 기준이다. 팀이 쓰는 교재나 사내 기준이 있으면 요약 노트를 프로필 `<고문>.knowledge_dir` 에 두면 그 노트를 먼저 따른다. 노트 원문은 리포트에 옮기지 않으므로 비공개 자료여도 된다.
- **최적화 고문은 측정 파일이 있어야 병목을 말한다.** 측정이 없으면 코드에서 찾은 것은 "후보"로만 적고, 첫 결과물은 측정 계획이다.
- **Godot 지원은 바꿔 읽기다.** 고문 문서는 언리얼 기준이고, Godot 에서는 [engine-godot.md](shared/engine-godot.md) 의 표대로 바꿔 읽는다. 표에 없는 언리얼 전용 단계는 "Godot 에 해당 없음"으로 건너뛴다. 기술 목록과 모듈 지도의 사용 흔적·참조는 텍스트로 보이는 것(res:// 경로, class_name, autoload, 씬의 ext_resource, C# namespace, 한 모듈에서만 선언한 C# 형 이름)만 센다. 여러 모듈이 같은 이름으로 선언한 C# 형, GDExtension 이 등록한 클래스, 이진 리소스(.res, .scn) 안의 참조는 세지 못한다. 자체 테스트 러너는 후보와 test_ 함수 수까지만 찾고, 확인 수는 세지 못한다. Godot 에는 정해진 측정 파일이 없어서, 최적화 고문이 병목을 말하려면 게임 안 측정 스크립트가 남긴 프레임별 CSV 가 있어야 한다. 그 파일에 "(확인 필요)"가 붙은 명령·클래스 이름은 대상 버전 문서로 확인한 뒤에 쓴다.
- **에이전트 이름 호출.** 스킬은 `advisors:web-scout`, `advisors:analyst` 를 이름으로 부른다. 이 이름을 찾지 못하는 환경이면 메인 대화에서 같은 규칙으로 수집하고, 리포트에 그 사실을 적는다.
