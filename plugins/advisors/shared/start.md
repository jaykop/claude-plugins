# 고문 공통 시작·마무리 절차

각 고문 스킬의 Step 0 과 Step Final 은 이 파일을 따른다. 대화 중에 사용자가 리포트의 잘못을 말할 때의 절차("결과 표시 받기")도 여기에 있다. 아래에서 `<고문>` 은 플러그인 `skills/` 아래 폴더 이름(design · newtech · market · perf · pm · td) 가운데 하나다. 질문이 다른 고문의 일로 보이면 `shared/routing.md` 를 본다.

이 파일은 Read 로 읽으므로 경로 변수가 바뀌지 않는다. `<플러그인 폴더>`, `<프로젝트 루트>` 는 SKILL.md '경로와 인자'에 적힌 실제 경로로 바꿔 쓴다.

## Step 0 — 시작

### 0-A. 실행 방식 판별
- SKILL.md '경로와 인자'에 적힌 이번 호출의 인자에 `--unattended` 가 있으면 무인 실행이다. 이후 모든 단계에서 `rules.md` §10 을 따른다(질문 금지, 리포트 저장까지만).
- 요청 문장의 낱말로는 판별하지 않는다. "무인도 생존 게임 시장성 봐 줘"처럼 '무인'이 들어간 요청도 대화 실행이다.
- 그 밖에는 대화 실행이다.

### 0-B. 공통 규칙 읽기
`<플러그인 폴더>/shared/rules.md` 를 읽는다. 이 규칙은 고문별 지침보다 우선한다.

### 0-C. 프로필 확인
프로필 위치는 `<프로젝트 루트>/.claude/advisors/profile.md` 하나다.

**있으면** 읽는다. 이 고문에 필요한 칸(각 SKILL.md 의 "필요한 프로필 값". 다른 고문 섹션의 칸이 적혀 있어도 포함한다)이 비어 있으면:
- 대화 실행: 그 칸만 한 번에 묻는다. 단, 다음 칸은 묻지 않는다.
  - SKILL.md 가 "Step 0 에서 묻지 않음"이라고 표시한 칸. 표 제목에 붙어 있으면 그 표의 모든 칸이다(그 스킬이 뒤 단계에서 따로 확인한다).
  - 사용자가 이미 "모름"이나 "아직 안 정함"이라고 답한 칸. 이런 답은 값을 비운 채 주석에 `[사용자] 모름` 으로 적어 두고, 다음부터 묻지 않는다. 사용자가 직접 값을 넣으면 그때부터 쓴다.
  - 사용자가 "없음"이라고 답한 목록 칸(예: 검색 금지어). 빈 목록 `[]` 에 주석 `[사용자] 없음` 을 달아 두고, 채운 칸으로 본다. 다음부터 묻지 않는다.
  - 파일에서 찾을 수 있는 칸. 묻지 않고 0-D 의 스크립트로 채운다.

  답을 받으면 프로필에 써 넣고 `updated` 를 오늘 날짜로 바꾼다. 값 옆 주석에 출처(`[사용자]`, `[파일]`, `[추정]`)를 단다.
- 무인 실행: 묻지 않는다. 빈 칸은 리포트의 "확인 못 한 것"에 적고, 그 칸이 꼭 필요한 단계는 건너뛴다.

**없으면**:
- 대화 실행: "이 프로젝트에 고문 프로필이 없어요. 만들까요?"라고 묻는다. 동의하면 0-D 를 진행한다. 거절하면 그 SKILL.md 의 "프로필이 없을 때" 단락이 정한 범위만 한다. 그 단락이 없는 고문은 프로필 없이 할 수 있는 범위(웹 조사 등)만 한다. 이때 웹을 쓰는 고문은 검색하기 전에 검색 금지어와 금지 조합을 한 번 묻고, 답은 이번 실행에만 쓴다. 어느 쪽이든 그 사실을 리포트 머리에 적는다.
- 무인 실행: `report_dir` 를 알 수 없으므로 아무것도 쓰지 않고, 최종 응답에 "프로필 없음 — 대화 세션에서 먼저 프로필을 만들어 주세요"만 남기고 멈춘다.

### 0-D. 프로필 만들기
1. 양식 `<플러그인 폴더>/shared/profile-template.md` 를 읽는다.
2. 파일에서 알 수 있는 값을 스크립트로 모은다.
   ```
   python "<플러그인 폴더>/scripts/profile_scan.py" "<프로젝트 루트>"
   ```
   `python` 이 없으면 `python3` 로 실행한다. 결과(버전 관리 종류, 프로젝트 파일, 엔진 버전, 문서가 많은 폴더 등)는 `[파일]` 출처로 채운다.
3. 남은 칸 중 **공통 칸과, 지금 부른 고문의 "필요한 프로필 값"에 적힌 칸만** 묻는다(0-C 의 "Step 0 에서 묻지 않음" 예외는 같다). 나머지 칸은 그 칸이 필요한 고문을 처음 부를 때 묻는다. 한 번에 다 묻고, 모르는 값은 비워 둬도 된다고 알려 준다.
4. 특히 다음은 추측으로 채우지 않는다: `decision_owners`, `user_role`, `team_size`, `search_banned_terms`, `search_banned_combos`, `design.principles_status`, `perf.budgets`.
5. 저장 위치는 `<프로젝트 루트>/.claude/advisors/profile.md`. 버전 관리에 올릴지는 사용자에게 맡긴다. git 프로젝트이고 `share_scope` 가 personal 이면 `.gitignore` 에 넣을지 묻는다.

### 0-E. 리포트 폴더와 지난 기록
모드가 정해져 있어야 직전 리포트를 고를 수 있다. 요청 문장으로 모드가 정해지지 않았으면 SKILL.md 의 모드 판별을 먼저 하고 0-E 로 온다.

1. `report_dir` 를 정한다. 상대 경로면 프로젝트 루트 기준이다. 폴더가 없으면 만든다.
2. `<report_dir>/<고문>/` 에서 **이번과 같은 모드**의 가장 최근 리포트를 찾는다(파일 이름의 모드 부분으로 가린다. `rules.md` §12). SKILL.md 가 대상까지 같아야 한다고 정했으면(예: 영역 진단은 같은 영역) 그 조건도 맞춘다. 찾으면 "직전 리포트"로 삼는다.
3. `<report_dir>/_state/inbox.md` 에서 받는 고문이 `<고문>` 이고 상태가 "열림"인 질문을 찾는다.
   - 대화 실행: "<고문> 앞으로 미해결 질문이 N건 있는데 이번에 같이 볼까요?"라고 묻는다. 같이 보기로 했으면 요청받은 일을 먼저 끝낸 뒤, 질문 하나를 이 고문의 '대상 하나를 보는 모드' 한 번으로 처리한다(SKILL.md 의 모드 판별 참고).
   - 무인 실행: 요청받은 모드의 범위에 맞는 질문만 넣고, 나머지는 리포트의 "확인 못 한 것"에 "다음 대화 실행에서 처리"로 적는다.
   - 예외: 받는 고문의 일이 아닌 질문(`shared/routing.md`)은 대화·무인 모두 사용자에게 묻지 않고 inbox-format.md 의 넘기는 규칙대로 맞는 고문 앞으로 넘긴다.
4. 오늘 날짜를 `date +%F` 로 정한다.
5. 기준 리비전을 읽는다. 프로필 `vcs_read_commands` 에 허용된 명령일 때만 읽고, 대화·무인 실행 모두 같다(`rules.md` §7). git 이면 `git rev-parse --short=12 HEAD`, p4 면 프로젝트 루트에서 `p4 changes -m1 ...#have`. 허용되지 않았거나 실패하면 "확인 못 함".

### 0-F. 팀 기준 노트와 결과 표시
판정 기준을 이 프로젝트에 맞추는 자료 두 가지를 읽는다. 읽고 쓰는 규칙은 `rules.md` §13 이다. 대화·무인 실행 모두 읽는다.

1. **팀 기준 노트**: 프로필 `<고문>.knowledge_dir` 가 비어 있으면 건너뛴다(Step 0 에서 묻지 않는다). 있으면 그 폴더의 `index.md` 를 먼저 읽고, 거기 적힌 노트 가운데 이번 모드와 대상에 걸리는 것을 읽는다. `index.md` 가 없으면 폴더의 .md 를 모두 읽는다. 폴더가 없거나 읽지 못하면 리포트의 "확인 못 한 것"에 적는다.
2. **결과 표시**: `<report_dir>/_state/feedback.md` 에서 고문 칸이 `<고문>` 이고 상태가 "반영 전"(빈 칸 포함)인 행을 읽는다(형식: `shared/state-formats.md`). 파일이 없으면 건너뛴다.
   - 행마다 그 리포트의 항목을 연다. 리포트 파일이 없으면 설명 칸만 본다.
   - 이번 판정에서 같은 잘못을 하지 않는다. 같은 잘못이 다시 나올 수 있는 곳(같은 종류의 질문, 같은 자료, 같은 판정)에서는 리포트의 그 자리에 행 ID 를 적고 이번에는 어떻게 했는지 한 줄 쓴다.
   - 표시가 근거와 맞지 않아 보이면(근거 파일:줄이나 출처가 표시와 어긋나면) 이번 판정을 표시에 맞춰 바꾸지 않는다. 리포트의 "결정이 필요한 것"에 행 ID 와 그 근거를 적어 사용자에게 다시 확인받는다.
   - 리포트 머리 "범위"에 읽은 행 ID 를 적는다(예: "결과 표시 FB-0003, FB-0007 읽음"). 읽을 행이 없으면 "결과 표시 없음"이다.
   - 원인이 비었거나 "모름"인 행은, 대화 실행이면 리포트 항목을 다시 보고 원인을 가린다. Step Final 에서 그 칸에 쓴다. 가리지 못하면 "모름"으로 둔다. 무인 실행이면 그대로 둔다.
   - 읽은 행이 10개 이상이면 정리를 제안한다. 대화 실행은 Step Final 의 후속 제안에 "반영 전 표시가 N건 쌓였어요. 원인별로 고칠 곳을 정리해 드릴까요?"를 넣는다. 동의하면 대화에 원인별 묶음(행 ID, state-formats.md "원인별 고칠 곳"의 후보)을 내고, 파일은 고치지 않는다. 무인 실행은 리포트 머리 "범위"에 "반영 전 N건 — 정리 필요"를 적는다.

## Step Final — 마무리

1. 리포트를 `<report_dir>/<고문>/<YYYY-MM-DD>-<모드>.md` 로 저장한다. 양식은 `<플러그인 폴더>/shared/report-base.md`.
2. 이 고문의 `_state` 파일을 갱신한다. 머리의 `마지막 갱신` 은 오늘 날짜로 바꾸고, `다음 점검:` 줄도 갱신한다. 세션 시작 알림은 이 두 값을 보고 알릴지 정한다. SKILL.md 가 파일마다 고치는 때를 정해 두었으면(예: td 의 td-debt.md 는 기술 부채 점검 때만) 그 파일은 그때만 고친다.
   - 결과 표시 기록(`_state/feedback.md`)은 대화 실행에서만 쓴다. 이번 실행에서 받은 표시(아래 "결과 표시 받기")와 0-F 에서 가린 원인을 쓴다. 파일이 없으면 `shared/state-formats.md` 의 머리로 만든다. 무인 실행에서는 쓰지 않는다.
3. 다른 고문에게 넘길 질문이 있으면 `_state/inbox.md` 에 추가한다(형식: `<플러그인 폴더>/shared/inbox-format.md`). 이번에 답한 질문은 상태를 "답함"으로 바꾼다.
4. 대화 실행이면 대화에 다음만 낸다.
   - 요약 세 줄
   - 결정이 필요한 것
   - 리포트 경로
   - 후속 제안 1~3개. 예:
     - "<다른 고문>에게 넘긴 질문 N건을 지금 볼까요?"
     - "<항목>을 코드 수정으로 넘길까요?" (프로필 `code_change_entry` 가 있으면 그 스킬 이름을 쓴다)
     - 이 고문을 처음 돌렸고, SKILL.md 의 기본 주기가 "예약 없음"이 아니고, 예약된 점검이 없으면: "다음 점검을 <주기>로 예약할까요?"
     - 0-F 에서 읽은 반영 전 행이 10개 이상이면: "반영 전 표시가 N건 쌓였어요. 원인별로 고칠 곳을 정리해 드릴까요?"
5. 무인 실행이면 최종 응답을 리포트 경로와 요약 세 줄로 끝낸다.

### 파일 쓰기 승인
각 SKILL.md 의 allowed-tools 는 프로젝트의 `.claude/advisors/` 아래(기본 `report_dir` 와 프로필 위치) 쓰기만 미리 허용한다. `report_dir` 를 다른 곳으로 정했으면 대화 실행에서는 파일마다 쓰기 승인을 묻는다. 무인 실행은 `rules.md` §10 마지막 항목을 따른다.

## 결과 표시 받기

대화 실행 중 사용자가 리포트의 잘못을 말하면("이 리포트 X 틀렸어", "이건 어디에나 맞는 말이야", "Y 는 안 봤네") 결과 표시 기록에 한 줄을 더한다. 리포트를 낸 뒤든 작업 중이든 같다. 무인 실행에서는 쓰지 않는다. 형식은 `shared/state-formats.md` 의 feedback.md 다.

1. 표시를 틀림 / 일반론 / 놓침 가운데 하나로 정한다. 사용자 말로 정해지지 않으면 셋을 보여 주고 한 번 묻는다.
2. 리포트와 항목을 정한다. 사용자가 짚지 않았으면 가장 최근 리포트에서 해당하는 항목을 찾아 보여 주고 맞는지 확인받는다. 다른 고문의 리포트를 두고 한 말이면 고문 칸은 그 리포트를 쓴 고문이다.
3. 설명 칸에는 사용자 말을 한 줄로 옮긴다. 다른 말로 바꿔 쓰지 않는다.
4. 원인을 가린다. 리포트 항목, 그때 읽은 자료(리포트 "범위"), 그 고문의 지침을 보고 state-formats.md "원인별 고칠 곳" 표의 다섯 가운데 하나를 고른다. 사용자에게 분야 지식을 요구하는 질문은 하지 않는다. 가리지 못하면 "모름"이다.
5. 상태는 "반영 전", 고친 곳은 비운다. 파일 쓰기는 Step Final 의 2 와 같다. 리포트를 이미 낸 뒤라면 바로 쓴다.
6. 대화에는 행 ID, 원인, 고칠 곳 후보만 한 줄로 알린다. reference·스크립트·SKILL.md·팀 기준 노트는 고치지 않는다(`rules.md` §13). 고칠 곳이 프로필 칸이면 0-C 처럼 사용자가 값을 확정한 뒤 프로필에 쓴다.
7. 사용자가 고친 곳을 알려 주거나("고쳤어, 커밋 abc") 반영하지 않기로 하면("반영 안 해도 돼, <이유>") 그 행의 고친 곳과 상태를 사용자 말대로 바꾼다.

## 예약 점검 만들기

사용자가 예약에 동의했을 때만 만든다.

- 세션에 예약 작업 도구(Claude Desktop 의 scheduled-tasks `create_scheduled_task`)가 있으면 그것으로 만든다.
  - 예약 실행은 이 대화를 기억하지 못한다. 지시문에 다음을 모두 넣는다.
    - 첫 줄: 부를 스킬과 모드, 그리고 `--unattended` 인자. 예: `/advisors:newtech 정기 점검 --unattended`. 무인 실행은 이 인자로만 판별된다(0-A). 슬래시 명령으로 읽히도록 이 줄을 맨 앞에 둔다
    - 프로젝트 루트의 절대 경로, 그리고 그 폴더에서 작업하라는 지시
    - "질문하지 말고 리포트 저장까지만 할 것". 사람이 읽는 설명이고, 판별은 첫 줄의 인자로 한다
    - `report_dir` 의 절대 경로. 예약 작업의 권한 설정에서 이 폴더 쓰기를 허용해 달라고 사용자에게 알린다. 각 SKILL.md 의 allowed-tools 는 `.claude/advisors/` 아래 쓰기와 git·p4 읽기 명령 몇 개만 미리 허용한다. `report_dir` 가 다른 곳이거나 `vcs_read_commands` 에 다른 명령이 있으면 그것도 허용해 달라고 알린다. 그 고문의 `knowledge_dir` 가 프로젝트 밖이면 그 폴더 읽기도 허용해 달라고 알린다
  - 주기는 각 SKILL.md 의 "기본 주기"를 제안하고 사용자가 정한 값을 쓴다.
  - Claude Desktop 앱이 켜져 있을 때 돌고, 꺼져 있었으면 다음에 앱을 켤 때 돈다는 점을 알려 준다.
- 예약 작업 도구가 없으면 직접 만들지 않는다. 사용자에게 Claude Desktop 의 예약 작업 화면에서 위 지시문으로 만드는 방법을 안내한다. 클라우드 예약(routines)은 로컬 파일을 볼 수 없으므로 권하지 않는다.
