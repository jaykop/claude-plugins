# 고문끼리 함께 읽는 기록 파일 형식

`<report_dir>/_state/` 의 파일 가운데 **다른 고문이 읽는 것**만 형식을 여기서 고정한다. 한 고문만 쓰고 읽는 파일(design-proposals, newtech-watchlist, market-snapshot, perf-ledger)의 형식은 각 스킬의 reference 에 있다.

모든 `_state` 파일의 첫 부분은 같다.

```markdown
# <파일 제목>

다음 점검: YYYY-MM-DD        (또는 "마일스톤 N일 전", "조건 — <조건 설명>". rules.md §12)
작성: <고문> / 마지막 갱신: YYYY-MM-DD / 기준 리비전: <CL 또는 커밋>
```

## newtech-inventory.md — 프로젝트 기술 목록

- 만드는 고문: newtech. 읽는 고문: perf, design(구현 확인 보조).
- 다시 만드는 조건: 엔진 버전 파일, 프로젝트 파일(.uproject 등), Config 폴더, 게임 코드의 빌드 설정(Build.cs)이 바뀌었을 때, 또는 마지막 갱신이 프로필 `stale_after_days` 보다 오래됐을 때. 어느 쪽도 아니면 다시 만들지 않고 날짜만 확인한다.
- 아래 표에 행을 더해도 된다(예: 프로젝트 모듈, 프로젝트 파일의 대상 플랫폼, 입력 지문). 끝에 `## 만든 방법과 검색 기록` 을 둬서 검색 범위, 상한, 실패 여부, 직전 목록과 달라진 것을 적는다.

```markdown
## 엔진
| 항목 | 값 | 근거 위치 |
|---|---|---|
| 엔진 버전 | 5.x.y | Engine/Build/Build.version |
| 소스 빌드 여부 | 예 / 아니오 | 프로젝트 파일의 EngineAssociation |
| 엔진 수정 블록 수 | N (폴더별) 또는 "검색 실패" | 프로필 newtech.engine_mod_dirs, 검색 패턴 |

## 플러그인·기능
| ID | 이름 | 상태 | 근거 위치 |
|---|---|---|---|
| TI-001 | ... | 사용 중 | ... |

상태는 다섯 가지 중 하나: 없음 / 엔진에 있으나 꺼짐 / 켜짐·사용 흔적 없음 / 사용 중 / 엔진을 고쳐서 씀

"엔진에 있으나 꺼짐"은 프로젝트 폴더에 있지만 꺼 둔 플러그인에도 쓴다. 텍스트로 확인할 수 없는 사용(에셋에서만 쓰는 경우)이 있으므로, 목록에 없다는 것만으로 "없음"이라고 하지 않는다.

## 주요 렌더링·네트워크 설정
| 설정 | 값 | 근거 위치 |
|---|---|---|
```

## market-competitors.md — 경쟁작 목록

- 만드는 고문: market. 읽는 고문: design(선례를 고를 때 먼저 본다).
- design 이 이 목록 밖의 게임을 선례로 쓸 때는 리포트에 "선례 전용"이라고 표시한다.

```markdown
| ID | 게임 | 식별자 | 묶음 | 플랫폼 | 출시일 | 수익 모델 | 선정 근거 | 마지막 확인일 |
|---|---|---|---|---|---|---|---|---|
| MC-001 | ... | steam:<앱 ID> | 직접 경쟁 | ... | ... | ... | ... | ... |
```

식별자는 다시 조회할 때 쓰는 값이다. Steam 게임은 `steam:<앱 ID>`, 그 밖에는 스토어 페이지 URL 을 쓴다. 없으면 "없음".

묶음은 다섯 가지 중 하나: 직접 경쟁 / 기준작(장르를 대표하는 성공작) / 부진 사례 / 이용자 시간 경쟁(과금은 달라도 같은 이용자의 시간을 쓰는 게임) / 선례 전용

## source-checks.md — 바깥 사실과 출처 확인 기록

- 쓰는 고문: newtech, market. 읽는 고문: 모두.
- 두 고문이 같이 쓰므로 행마다 "쓴 고문" 칸을 채운다. 다른 고문이 넣은 행은 지우지 않는다. 다시 확인했으면 값·확인일·다시 확인할 날짜를 갱신해도 된다. 이때 "쓴 고문"은 처음 넣은 고문 그대로 둔다.
- 머리의 `다음 점검:` 은 두 표의 모든 행 가운데 가장 이른 "다시 확인할 날짜"로 정한다. 어느 고문이 쓰든 같은 규칙이다.
- 지침 본문에 날짜가 붙은 바깥 사실(최신 엔진 버전, 행사 일정, 기능의 성숙도 등)을 박지 않는다. 그런 사실은 이 파일에 확인일과 함께 두고, 다시 확인할 날짜가 지나면 새로 확인한다.

```markdown
## 바깥 사실
| ID | 사실 | 값 | 출처 URL | 출처 종류 | 쓴 고문 | 확인일 | 다시 확인할 날짜 |
|---|---|---|---|---|---|---|---|
| SC-001 | 최신 엔진 정식 버전 | 5.x | ... | 1차 | newtech | YYYY-MM-DD | YYYY-MM-DD |

## 출처 접근 가능 여부
| 출처 | 방식 | 결과 | 쓴 고문 | 확인일 | 다시 확인할 날짜 | 메모 |
|---|---|---|---|---|---|---|
| ... | 자동 조회(WebFetch) / 스크립트 / 사람이 내보내 줘야 함 | 열림 / 막힘(코드) / 부분 / 도구가 막음 | market | YYYY-MM-DD | YYYY-MM-DD | |

결과의 "도구가 막음"은 사이트가 아니라 Claude Code 의 웹 도구가 그 주소를 열지 않는 경우다("unable to fetch", "not accessible" 같은 오류). 이 경우 다른 방법으로 돌아가지 않고 "사람이 내보내 줘야 함"으로 분류한다.
```

## 프로필에 올리는 값

여러 고문이 쓰는 값은 `_state` 가 아니라 프로필에 둔다. 예: 대상 사양(`target_spec`), 타깃 이용자(`market.target_player`), 측정 장면(`perf.scenarios`).

- 고문이 이 값을 바꾸자고 할 때는 직접 고치지 않는다. 리포트의 "결정이 필요한 것"에 바꿀 값과 근거를 적고, 사용자가 확정하면 그때 프로필에 쓴다.
- 하드웨어 보급 분포는 market 만 조회한다. newtech 와 perf 는 프로필의 `target_spec` 만 읽는다.
