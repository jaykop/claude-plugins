# 설명 변경 기록 (작성 쪽)

작업마다 바꾼 설명과, 로직 변경으로 실제 동작과 달라진 기존 설명을 목록에 남긴다. 검토하는 쪽은 이 목록의 항목과 근거 구현만 읽고 교정한다. 목록 형식과 명령은 `<플러그인 폴더>/shared/queue-format.md` 에 있다. 필요한 단락만 읽는다.

## 경로

- 플러그인 폴더: `${CLAUDE_PLUGIN_ROOT}`
- 프로젝트 루트: `${CLAUDE_PROJECT_DIR}`

값이 변수 이름 그대로 보이면 플러그인 폴더는 이 SKILL.md 의 두 단계 위 폴더, 프로젝트 루트는 세션을 시작한 폴더다. 명령은 프로젝트 루트에서 실행한다.

```
python "<플러그인 폴더>/scripts/review_queue.py" <명령> <task> ...
```

`python` 이 없으면 `python3` 을 쓴다. Windows 콘솔에서 `UnicodeEncodeError` 가 나면 `python -X utf8` 로 실행한다. 출력 중 오류가 났다고 기록까지 저장됐다고 가정하지 말고 목록 파일을 읽어 확인한다.

## 시작 전

1. 프로필(`<프로젝트 루트>/.claude/ko-review/profile.md`)을 읽는다. 없으면 목록을 쓸지 묻고, 쓰기로 하면 양식(`shared/profile-template.md`)으로 만든다. 이때 `queue_dir` 은 반드시 확인받는다. 공개 저장소라면 git 에서 빠지는 폴더여야 한다.
2. `git status --short` 와 작업 메모를 읽는다. 작업 ID 는 이슈가 있으면 `<번호>-<slug>`, 없으면 `<slug>` 다. 같은 작업의 열린 목록이 이미 있으면 새로 만들지 않고 이어 쓴다. 닫힌 목록은 다시 열지 않는다. 보관 폴더로 옮겨졌으면 같은 ID 로 새로 `start` 한다.
3. **파일을 고치기 전에** 고칠 파일을 명시적으로 나열해 시작 상태를 남긴다. 폴더 전체를 넘기지 않는다.

   ```
   python "<플러그인 폴더>/scripts/review_queue.py" start <task> --issue <번호> --paths <파일들>
   ```

   작업 중 새 파일을 고치게 되면 고치기 전에 `scope <task> --paths <파일들>` 로 더한다. 이미 고친 뒤에 더했다면 시작 전 차이를 되살릴 수 없으므로 그 사실을 작업 메모와 항목의 `reason` 에 적는다.

## 끝날 때

구현과 관련 문서 반영을 마쳤거나 사용자 빌드·실행 확인을 기다리기 **전에** 기록한다. 후속 질문이나 확인을 기다리느라 미루지 않는다.

1. `capture <task>` 로 시작 상태와 다른 파일과 diff 구간을 기록한다. 이미 커밋했어도 시작 상태와 다른 파일은 기록된다.
2. 바꾼 설명마다 항목을 만든다. 항목 JSON 을 `queue_dir` 아래(예: `<queue_dir>/<task>.items.json`)에 쓰고 `register <task> --items <그 파일>` 로 등록한다.
   - 등록 전에 프로필 `queue_scope` 를 확인한다. 설명 파일이 그 패턴에 맞지 않거나 `exclude` 에 걸리면 항목으로 만들지 않고 `no-impact` 로 남긴다. `queue_scope` 가 비었으면 제한하지 않는다. 범위 밖 항목이 섞이면 도구가 등록 전체를 거절한다.
   - `selector` 는 설명의 위치, `evidence` 는 그 설명을 뒷받침하는 구현·계약의 위치다. 근거는 기본값·해당 분기·종료 처리처럼 설명을 확인하는 데 필요한 범위를 고른다.
   - 설명을 고치지 않았어도 구현 변경으로 기존 설명이 실제 동작과 달라졌다면 그 설명을 등록한다.
   - 같은 id 를 다시 등록하면 그 항목은 다시 대기가 된다. 검토 뒤 설명이나 근거를 또 고쳤을 때 쓴다.
3. 설명에 영향이 없는 변경은 `no-impact <task> --path <파일> --note "이유"` 로 남긴다.
4. `pending <task>` 출력의 `unassignedChanges` 와 실제 변경 구간을 비교해 빠진 기록을 채운다. 이 알림은 파일 단위다. 파일에 항목이 하나 있다고 그 파일의 모든 변경이 등록됐다고 보지 않는다.

## 커밋한 뒤 닫기

목록은 그 작업의 커밋 전 검토를 위한 기록이다. 작업을 커밋하고 프로젝트가 정한 검토 넘기기를 마쳤으면 목록을 닫는다. 닫힌 목록은 이후 다른 작업의 변경으로 다시 대기가 되지 않는다. 자세한 규칙은 `queue-format.md` 의 "목록 수명" 단락에 있다.

1. `pending <task>` 로 남은 항목을 본다.
2. 위치 오류 항목(`locationError`)을 처리한다. 파일 이름이나 문장이 바뀌어 위치만 어긋났으면 목록의 경로·anchor 를 고친다. 설명 자체가 지워졌거나 다른 작업의 설명으로 넘어갔으면 `retire <task> --id <id> --note "<이유와 대체 작업>"` 로 폐기한다.
3. `needs-decision` 항목은 프로젝트의 이슈 댓글 초안이나 작업 메모로 옮긴다. 판단은 사용자가 한다.
4. `close <task> --note "<커밋과 검토 결과 요약>"` 로 닫는다. 남은 대기 항목이 있으면 도구가 거절하고 그 항목을 출력한다. 남긴 채 닫는 것은 사용자에게 항목을 보여 주고 확인받은 뒤 `--allow-unresolved` 를 붙여서만 한다.
5. 같은 작업의 등록 입력 파일(`<task>.items*.json`)은 지워진다. 프로필 `queue_archive_dir` 이 있으면 목록이 보관 폴더로 옮겨진다. 완료 보고에 옮겨진 경로를 적는다.

## 지키는 것

- 이 기록은 설명의 인계 절차다. 문장 품질이나 빌드·실행 확인의 근거로 쓰지 않는다. 빌드·테스트·검사를 실행하지 않는다.
- 검토하는 AI 를 자동으로 부르거나 메시지를 보내지 않는다. 검토 요청은 사용자가 전달한다.
- 검토하는 쪽이 같은 목록을 고치는 중일 수 있다. 쓰기 직전에 목록을 다시 읽고, 동시에 고치지 않는다. 도구가 "Queue changed" 로 거절하면 다시 읽고 이어서 진행한다.
- 완료 보고에 목록 경로와 대기 항목 수, 판단이 필요한 항목을 적는다.
