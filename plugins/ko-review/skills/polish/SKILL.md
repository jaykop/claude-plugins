# 한국어 기술 문서와 주석 다듬기

독자가 문장을 다시 해석하지 않고 무엇을 설정하며 어떤 결과를 얻는지 알 수 있게 쓴다. 사실이 맞는지와 설명이 읽히는지를 각각 판단한다. 금지어가 없거나 예전에 검토한 문장도 이 판단을 생략하지 않는다.

## 경로와 우선순위

- 플러그인 폴더: `${CLAUDE_PLUGIN_ROOT}`
- 이 스킬 폴더: `${CLAUDE_SKILL_DIR}`
- 프로젝트 루트: `${CLAUDE_PROJECT_DIR}`

값이 변수 이름 그대로 보이면 이 스킬 폴더는 이 SKILL.md가 있는 폴더, 플러그인 폴더는 그 두 단계 위, 프로젝트 루트는 세션을 시작한 폴더다. 아래 경로 자리에는 실제 경로를 넣는다.

사용자의 현재 요청 → 프로젝트 지침 → 이 스킬 순으로 따른다. 프로필은 `<프로젝트 루트>/.claude/ko-review/profile.md`이고 양식은 `<플러그인 폴더>/shared/profile-template.md`다. 프로필의 `instructions`를 읽고, 없으면 `AGENTS.md`·`CLAUDE.md`를 읽는다. 프로필이 없으면 지정받은 범위로 진행한다. 프로필 생성은 작업의 선행 조건이 아니다.

## 범위를 정하고 읽기

1. 버전 관리 상태(`git status --short` 또는 `p4 opened`)와 대상 파일의 현재 내용을 읽는다. 다른 작업자의 변경을 보존한다.
2. 지정받은 파일·문단을 대상으로 삼는다. 넓은 범위를 요청받으면 `doc_roots`·`code_roots`·`data_comment_files`로 실제 파일 목록을 만들고 `exclude`, 벤더, 생성 파일을 뺀다. 템플릿은 작성 기준으로 읽되 사용자가 교정을 요청하면 그 자체도 포함한다.
3. 전수 교정은 파일 목록을 기준으로 진행한다. 표의 셀, 목록, 짧은 한 줄 주석도 읽는다. 검색은 누락을 줄이는 보조 수단이다. 검색에 걸리지 않은 문장을 검토한 것으로 세지 않는다. 분량을 나누면 읽은 범위와 남은 범위를 기록한다.
4. 한 설정의 주석 블록, 문단, 표의 한 행처럼 뜻이 완결되는 단위로 읽고 고친다. 바뀐 단어나 검색된 한 줄만 보지 않는다. 인접 항목은 대상을 구분하는 데 필요한 만큼 읽으며, 무관한 항목까지 자동으로 고치지 않는다.

일반 문장 기준은 이 파일 하나를 쓴다. 참고 파일은 대상에 맞는 것만 함께 읽는다. 아래 네 파일 밖의 참고 파일은 없다.

| 대상 | 함께 읽는 파일 |
|---|---|
| 에디터·Blueprint에 노출되는 설명, 설정 파일의 설명 칸(`data-comment`) | `reference/editor-comments.md`. 프로필 `engine`이 `unreal`이면 `reference/unreal.md`도 |
| manual 문서 | `reference/manual.md` |
| 일반 코드 주석, devlog·plan 같은 그 밖의 문서 | 없음 |
| 낱말 판단이 막힐 때만 | `reference/word-choice.md` |

같은 세션에서 이미 읽은 파일은 다시 읽지 않는다. `review` 스킬에서는 문장 기준만 적용하고 기술 내용 판단은 그 스킬의 제한을 따른다.

## 작성·인계 단계에서 적용하기

이 기준은 교정할 때뿐 아니라 한국어 설명을 처음 쓸 때도 적용한다. 작성자는 쓰기 전에 이 파일의 "문장 기준"과 "교정 완료 판단", 위 표에서 대상에 맞는 참고 파일을 읽는다. 검토자는 검토를 시작할 때 같은 기준을 읽되, 사실을 판단할 권한은 `review` 등 자신이 맡은 절차의 제한을 따른다. 세션마다 한 번 읽으며, 설명이나 항목마다 다시 읽지 않는다. 긴 작업을 이어받거나 맥락이 압축돼 기준을 확인할 수 없을 때만 다음 설명을 쓰기 전에 해당 부분을 다시 읽는다. 작업 밖 문장까지 교정할 필요는 없다.

사용자의 짧은 말이나 작업 지시서는 사실·결정의 근거이며 산출물의 문체 견본은 아니다. 기존 문서와 전달받은 메모에서도 기술 사실과 문장 형태를 구분한다. 사용자가 산출물의 문체를 명시했으면 그 요청을 따르고, 대화 응답을 짧게 하라는 선호만 있으면 문서·주석의 문장까지 축약하지 않는다. 지시서와 검토 메모처럼 다음 작성자가 읽는 한국어 작업 자료도 대상·조건·결과의 관계가 드러나게 쓴다. 목록의 값·경로·식별자까지 문장으로 늘리지는 않는다.

짧게 쓰려면 반복과 독자에게 필요 없는 정보를 덜어낸다. 뜻을 구분하는 조사·어미·서술어와 적용 조건은 남긴다. 쉽게 설명하려면 필요한 관계나 개념의 역할을 밝힌다. 통용되는 한자어·전문 용어를 억지로 순우리말로 바꾸거나 문장을 길게 만드는 것을 목표로 삼지 않는다.

## 문장 기준

### 독자에게 필요한 사실부터 쓴다

설정을 고르는 사람, 함수를 호출하는 개발자, 구현을 유지보수하는 개발자가 알아야 할 내용은 다르다. 문장을 쓰기 전에 독자와 이 설명을 읽는 목적을 정한다. 첫 문장에 설정의 역할이나 함수의 결과를 쓴다. 조건·예외·실패 처리는 해당 사실 바로 뒤에 붙인다.

설정 툴팁에 구현자의 의무, 모듈 의존 이유, 수정 이력을 나열하지 않는다. 반대로 API 호출자가 지켜야 할 수명·정리·부작용·실패 조건은 중요한 정보다. 짧게 만들려고 이런 제약을 지우지 않는다. 독자의 선택이나 사용에 영향을 주는 정보인지로 판단한다.

### 대상을 이름으로, 동작을 결과로 설명한다

- 누가 무엇을 바꾸는지 밝힌다. `이 값`, `여기`, `위`, `그쪽`의 대상이 문장과 화면에서 하나로 정해지지 않으면 정확한 설정·객체 이름을 쓴다.
- `전이를 연다`, `값을 먹인다`처럼 다른 동작을 빌려 설명하지 않는다. 전이를 요청하는지, 허용하는지, 실행하는지 구분해 실제 동작을 쓴다. 이해에 필요한 단계를 생략한 비유는 친근한 말투여도 고친다.
- UI·API 이름과 확립된 전문 용어는 유지한다. 이름을 한국어로 번역해 새 개념을 만들지 않는다. 독자에게 생소하면 첫 사용에 역할을 짧게 설명한다. 영어로 옮길 수 있다는 이유만으로 직역투라 판정하지 않는다.
- 주어·목적어·서술어가 문맥에서 자연스럽게 이어지는지 읽는다. 실제 사물이 그 동작을 할 수 있는지만으로 문장을 통과시키지 않는다. `감쇠를 먹는다`, `무기를 벗는다`도 감쇠되는 값과 장착 해제 동작을 직접 쓰는 편이 분명하다.

### 조건과 결과를 한 번에 이해하게 쓴다

- 조건을 먼저 쓰고 그때의 결과를 잇는다. 빈 값은 무엇을 비웠는지, 어떤 검사·처리를 생략하거나 어떤 값을 대신 쓰는지 밝힌다.
- `비우면 통과한다`에서 무엇이 통과하는지, `조건으로 거르지 않는다`에서 무엇이 남는지 독자가 다시 해석해야 하면 고친다. 검사 하나를 생략하는 것과 전체 실행이 성공하는 것은 다르다. 나머지 조건까지 없어진 것으로 쓰지 않는다.
- 조건의 부정과 예외가 겹치면 상태별로 나눈다. `0`, 음수, 빈 참조, 실패를 같은 결과로 뭉뚱그리지 않는다. 모두 적는 것이 목적은 아니며, 해당 설정의 결과를 바꾸는 경우를 남긴다.
- `항상`, `즉시`, `최대`, `모두`는 확인된 범위에서만 쓴다. 필수·선택·권장은 구분한다. 선택이라는 사실을 잃고 무조건 `해야 한다`로 바꾸지 않는다.

### 읽는 순서와 문장 구조를 정돈한다

- 한 문장에는 중심 동작 하나를 둔다. 조건, 결과, 예외, 이유가 이어져 중간을 되짚어야 하면 문장을 나눈다. 글자 수나 어절 수를 통과 기준으로 삼지 않는다.
- 명사가 이어지거나 `~의`로 연결된 말에서 관계가 불분명하면, 누가 무엇을 하는지와 무엇을 기준으로 삼는지 풀어 쓴다. 필요한 조사·어미와 서술어를 보완한다. `~의`를 지우거나 쉬운 명사로 바꾸는 것만으로 관계가 분명해지지는 않는다.
- 본문의 설명은 서술어로 뜻을 맺는다. 제목·표의 셀·목록·짧은 툴팁은 항목 이름과 함께 뜻이 완결되는 구를 쓸 수 있다. `장애물을 판정하는 충돌 채널`은 유지할 수 있지만, 독자가 빠진 동작이나 결과를 추정해야 하는 토막말은 고친다.
- `~되어진다` 같은 겹친 피동, 잘못된 조사·호응, 지나치게 긴 수식어를 고친다. 자연스러운 상태 설명까지 억지로 능동문으로 바꾸지 않는다.
- 괄호·대시·콜론으로 이은 내용의 관계를 독자가 추정해야 하면 조건·이유·예시를 문장으로 밝히거나 문장을 나눈다. 문장부호 자체를 금지하지 않으며, 나란히 적힌 사실에 근거 없는 인과관계를 더하지 않는다.
- 같은 대상은 같은 용어로 부른다. 소스 대조, 빌드 성공, 실행 확인처럼 다른 사실은 구분한다. 문서의 기본 종결 방식을 따르고, 격식과 강조를 더해 품질을 대신하지 않는다.
- 비교는 표, 절차는 순서 목록을 쓸 수 있다. 각 표의 제목과 열의 역할에 내용이 맞는지 본다. 경고는 조건과 실제 위험을 설명한다.

## 사실과 수정 권한

표현을 고칠 때 보존할 것은 적용 조건, 부정, 대상 범위, 횟수, 단위, 기본값, 수명, 부작용, 실패 처리다. 원문의 비유, 문장 순서, 반복, 명사 토막, 독자와 무관한 설명까지 보존할 필요는 없다. 이미 명료하고 필요한 문장은 유지한다. 모든 문장을 다시 쓰거나 단어를 바꾸는 양으로 성과를 판단하지 않는다.

로직과의 일치 검토를 요청받으면 선언·초기값, 값을 읽는 분기, 조기 반환, 직접 호출 대상과 필요한 종료 경로를 읽는다. 이름이나 오래된 설계만으로 실행 동작을 정하지 않는다. 외부 API 동작을 단정해야 하면 해당 버전의 소스나 공식 문서를 근거로 삼는다. 설명이 틀렸다는 근거가 있으면 설명을 바로잡되, 코드 결함이나 미확정 설계로 보이면 쟁점을 보고한다. 주석에 맞추려고 코드를 바꾸지 않는다.

`review` 스킬에서는 이 기술 판단 절차로 범위를 넓히지 않는다. 원뜻이 분명한 부분의 표현만 고치며, 설명·근거가 충돌하거나 삭제할 내용이 사용 제약인지 불명확하면 `needs-decision`으로 남긴다.

- 코드 교정에서는 설명 주석만 바꾼다. 식별자, 문자열 리터럴, 메타데이터, 실행 로직을 보존한다. 설정 파일도 설명 칸 외의 키·섹션·연산자·등록 항목을 보존한다.
- 독자와 무관한 구현 설명은 요청 범위 안에서 적절한 구현 주석·문서로 옮길 수 있다. 범위 밖이면 옮길 위치를 보고한다. 삭제로 동작의 모순을 숨기지 않는다.
- 과거 확인 날짜·결과와 확인하지 않은 범위를 보존한다. 문장 교정을 새 실행 확인으로 기록하지 않는다. 실제 문서 갱신일은 수정일로 바꾼다.
- 파일의 인코딩(BOM 유무)과 줄바꿈을 유지한다. 무관한 서식 변경을 만들지 않는다.

## 교정 완료 판단

최종 문장을 원문과 나란히 보지 않고 독자가 읽는 자리에서 다시 읽는다. 다음을 모두 만족해야 교정을 마친다.

1. 설정·함수·절차의 대상과 역할을 바로 알 수 있다.
2. 결과가 달라지는 조건과 빈 값·실패의 결과를 해당 범위에서 알 수 있다.
3. 비유나 생략을 원래 기술 개념으로 다시 번역할 필요가 없다.
4. 이 독자에게 필요한 정보가 먼저 나오며, 관련 없는 구현 의무나 이력이 끼어 있지 않다.
5. 원문 또는 허용된 근거와 대조했을 때 기술 사실과 확인 상태가 보존된다.

`추가 조건`, `뜻이 분명하다`, `기존 표현을 유지했다`라는 말만으로 완료를 정당화하지 않는다. 조건 객체가 무엇을 판정하고 빈 값이 어느 검사에 영향을 주는지 설명할 수 있는지 본다. 수정이 필요 없으면 핵심 판단 근거를 짧게 기록한다.

## 보조 도구와 보고

`doc_check.py`는 Markdown의 링크·앵커·낱말 후보를 찾는다. 스크립트 출력에 “확인 필요 항목만 판단”이라고 나오더라도 요청 범위의 문장을 직접 읽는 절차를 대체하지 않는다. 소스 주석과 ini의 전수 교정 도구로 쓰지 않는다.

```
python "<플러그인 폴더>/scripts/doc_check.py" <문서들>
```

사용자·프로젝트의 검사 권한을 먼저 따른다. `check_runs: user`이거나 검사를 금지했으면 요청받지 않은 스크립트를 실행하지 않는다. `python`이 없으면 `python3`을 쓴다. 기본 위치 외의 낱말 목록은 `--terms <terms_file>`로 지정한다. 낱말 목록의 구분과 등록 기준은 `shared/terms-format.md`를 따른다. 새 금지어 등록은 요청받은 범위에서만 하며, 문맥 의존 표현을 일괄 금지하지 않는다.

맞춤법·문체 스킬이 설치돼 있으면 필요한 참고만 읽는다. 스킬을 쓰기 위해 다른 AI를 자동 호출하거나 검사 절차를 늘리지 않는다.

수정을 요청받았으면 권한 안의 교정은 직접 수행한다. 목록을 쓰는 작업이면 작성 쪽은 `record`로 등록하고 검토 쪽은 `review` 로 요청서에 적힌 결과 파일을 쓴다. 완료 보고는 실제로 읽고 고친 범위, 남은 모호한 내용, 실제 검사 여부를 적는다. 전수 교정에서는 미처리 범위도 밝힌다. 예전 `reviewed` 상태나 해시 일치를 현재 문장 품질의 근거로 삼지 않는다.

## 참고한 문장 기준

[snflkd/fluent-korean](https://github.com/snflkd/fluent-korean/tree/ce8683f0eba8cddb91de4dcd151425ff73e60498)(MIT, 기준 커밋 `ce8683f0eba8cddb91de4dcd151425ff73e60498`)의 문장·구 단위 기준을 참고해, 생략된 성분과 명사 사이의 관계를 풀어 쓰는 기준 및 문장부호로 함축한 관계를 밝히는 기준을 보완했다. 원문은 대화 출력용이며 코드 주석을 제외한다. 여기서는 프로젝트가 교정 대상으로 정한 한국어 설명 주석에도 필요한 문장 기준만 적용한다. 코드·식별자·일반 문자열·메타데이터의 수정 권한은 넓히지 않는다.

작성·인계 단계에서 기준을 읽는 시점, 대화 말투와 산출물 문체의 구분, 간결함을 위해 필요한 문장 성분을 생략하지 않는 기준은 fluent-korean 제작자 후기(사용자 제공, 2026-11-01)를 참고해 보완했다. 후기의 원인 추정이나 특정 모델에 대한 평가는 지침의 근거로 삼지 않았다.
