# 에디터·설정 파일에서 읽는 설명

설정 패널, 노드 메뉴, 스크립트에 노출된 API, 설정 파일의 설명 칸에서 읽는 설명은 **코드를 읽지 않고 에셋이나 데이터를 설정하는 사람**을 독자로 삼는다. 이 사람이 주석만 읽고 적용 조건과 결과를 알 수 있어야 한다.

## 범위 고르기

- 공개 헤더·공개 폴더인지만으로 대상을 정하지 않는다. 비공개 위치에 있어도 에디터에 노출되는 타입·설정이면 포함한다.
- 사용자가 파일을 지정했으면 그 범위부터 읽는다. 에디터 전반을 요청했으면 직접 만든 코드의 에셋·조건·태스크·컴포넌트 설정, 스크립트 노출 API, 그래프 노드를 먼저 본다. 벤더와 생성 파일은 뺀다.
- 검색으로 선언과 값을 쓰는 위치를 찾되, 걸린 문장만 바꾸지 말고 인접 주석·선언·관련 구현을 읽는다.

## 구현에 맞는 설명

고치려는 설정의 기본값, 값을 읽는 분기, 조기 반환, 정상 완료·취소·중단 경로를 필요한 만큼 확인한다. 함수가 다른 구현에 위임하면 직접 호출 대상까지 읽는다. 설명서는 현재 사용 방법을 확인하는 참고로 쓰고, 폐기된 설계 문서로 동작을 추정하지 않는다.

- 켜짐·꺼짐, 0·음수·빈 참조, 지원하지 않는 조합, 조건 평가의 조기 종료를 구분한다.
- 기준점(오브젝트 중심, 표면, 지정 지점)과 단위(초, 프레임, 도, 도/초, 미터, 센티미터)를 섞어 쓰지 않는다. 편집 화면의 입력 범위 제한이 실행 중 입력 검사까지 보장한다고 가정하지 않는다.
- 실행 중 대상을 갱신하는지, 시작 시점에 고정하는지, 끝날 때 무엇을 회수하는지 호출자에게 필요한 만큼 적는다. 외부 엔진의 동작이 쟁점이면 그 소스나 공식 문서를 읽는다.
- 주석이 오래됐으면 현재 구현에 맞춰 고친다. 구현 결함이나 사용 방법과의 충돌이 의심되면 근거와 확인하지 못한 부분을 기록한다. 주석에 맞추려고 로직이나 설계를 바꾸지 않는다.

## 문장

첫 문장은 설정의 역할이나 노드가 하는 일을 바로 설명하고, 다음 문장에 필요한 조건·단위·실패 처리를 적는다. `이 값`, `대상`, `기준`이 무엇을 가리키는지 모호하면 실제 대상을 쓴다. 비유·음역·명사 나열보다 주어와 서술어가 있는 문장을 쓴다. 뜻이 분명한 짧은 기존 문장은 그대로 둔다.

- `항상`, `즉시`, `반드시`는 그 조건에서 구현이 보장할 때만 쓴다. 설정의 목적이나 권장 예시를 결과 보장으로 바꾸지 않는다.
- 다른 설정·애니메이션·충돌처럼 바깥 요인의 영향을 받는 결과에는 적용 범위를 적는다.
- 직렬화 호환성, 모듈 의존 이유, 구현 이력처럼 설정하는 사람에게 필요 없는 정보는 일반 구현 주석으로 옮긴다. 개발자용 공개 API 에는 수명·부작용·실패 조건을 남긴다.
- API·UI 이름은 현재의 정확한 표기를 쓴다.

## 고치지 않는 것

- 실행 로직, 식별자, 기본값, 문자열, 표시 이름·분류·툴팁 같은 메타데이터 값은 그대로 둔다. 프로젝트가 메타데이터를 영어로 유지하면 그 규칙을 따른다.
- 파일은 원래 인코딩(BOM 유무)과 줄바꿈을 유지한다. 무관한 줄바꿈 변경을 만들지 않는다.
- 주석을 고쳐도 화면에 보이는 툴팁이 바뀌지 않는 구조가 있다(메타데이터가 주석보다 우선하는 경우 등). 화면을 확인하지 않았으면 UI 가 바뀌었다고 보고하지 않는다.
