# manual의 정보 배치와 문장

일반 문장 기준과 완료 판단은 상위 `SKILL.md`를 따른다. 이 파일은 사용법 문서의 배치를 정한다. 프로젝트 템플릿을 우선하며, 교정 요청을 문서 전체 개편 권한으로 해석하지 않는다.

## 읽는 순서

독자는 무엇을 할 수 있는지 알고, 설정한 뒤, 기대한 결과가 나오지 않을 때 확인할 곳을 찾는다. 같은 항목 안에서는 다음 순서로 배치한다.

1. 기능의 목적과 적용 범위
2. 준비할 대상과 사용 순서
3. 설정의 효과, 빈 값과 예외, 사용 제약
4. 증상별 확인 방법
5. 실제 확인한 범위와 관련 근거

템플릿에 확인 상태 머리말이 있으면 현재 확인 수준과 주요 미확인 범위만 짧게 쓴다. 날짜별 빌드·로그·수정 과정은 확인 상태 본문이나 devlog에 둔다. 확인되지 않았다는 사실을 숨기지 않으며, 이동하더라도 날짜·결과·범위를 보존한다. 지시서 작성 작업에서는 허용된 문서·문단 밖으로 옮기지 않는다.

## 사용 절차

- 단계마다 독자가 어디에서 무엇을 지정하거나 실행하는지 쓴다. 준비 사항, 설명, 실행, 결과 확인을 한 문장에 몰아넣지 않는다.
- UI·API 이름은 실제 이름을 쓰고, 처음 등장하는 개념은 필요한 만큼 설명한다. 내부 필드·구조 이름만 나열해 사용법을 대신하지 않는다.
- 설정 표는 값의 역할과 결과를 설명한다. 빈 값이 기본값 유지·생략·자동 선택·실패 중 무엇인지 구분한다. 모드에 따라 적용되지 않는 값은 해당 조건을 붙인다.
- “이번 변경”, “이전과 같다”처럼 세션을 알아야 이해할 수 있는 말은 현재 동작이나 정확한 기록 링크로 바꾼다. 과거 이력을 설명하는 devlog까지 현재형으로 바꾸지 않는다.

## 표·목록·체크리스트

짧은 항목도 직접 읽는다. 표의 열 제목과 해당 행을 함께 읽었을 때 뜻이 완결돼야 한다.

- “증상” 열에는 사용자가 관찰하는 현상을 쓴다. 구현 작업명·수정 이력은 증상이 아니다.
- “원인”과 “확인 방법”을 구분한다. 로그 문구를 옮긴 것만으로 원인을 확정하지 않는다. 추정은 추정으로 남긴다.
- 체크리스트는 조작과 관찰할 결과를 구분한다. 공간·단위·기준점을 생략하거나 “설 자리” 같은 임시 이름을 만들지 않는다. 에셋 이름과 화면의 실제 표식을 이용한다.
- 같은 설명을 머리말·설정 표·사용 순서에 반복하지 않는다. 단독으로 쓰이는 표에 꼭 필요한 조건은 남긴다.

## 구현 설명과 근거

설정 결과를 이해하는 데 필요한 원리는 가까이 둔다. 컨테이너 선택 이유, 엔진 내부 호출 경로, 수정 과정은 devlog나 API 문서에 두고 사용법에서 연결한다. 개발자용 확장 절차가 문서의 목적이면 그 독자에게 필요한 구현 정보는 유지한다.

`doc-draft` 같은 다른 작성 절차가 이 기준을 쓰더라도 새 사실을 조사하거나 추가할 권한이 생기지는 않는다. 제공된 사실의 순서와 문장을 다듬고, 빠진 사실은 그 절차가 정한 곳에 남긴다. 사실 대조와 실행 확인을 구분한다.
