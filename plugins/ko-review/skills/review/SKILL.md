# 설명 변경 부분 검토 (검토 쪽)

목록에 남은 대기 항목만 읽고 교정한다. 문장 기준은 같은 플러그인의 `polish` 스킬이고, 목록 형식과 명령은 `<플러그인 폴더>/shared/queue-format.md` 다. 필요한 단락만 읽는다.

## 역할

대기 항목의 주석·문서·설정 설명을 자연스러운 한국어로 교정한다. 코드 기능 검수, 버그 판단, 동작 추정은 하지 않는다.

- 근거 구현(`evidence`)은 교정한 문장이 원래 뜻을 바꾸지 않았는지 확인하는 데만 읽는다. 적용 조건, 부정, 횟수, 단위, 기본값, 실패 조건이 원문과 같은지 본다.
- 재현하지 않은 동작이나 한계를 설명에 새로 쓰지 않는다. 원문에 없는 조건·제한·이유를 더하지 않는다.
- 뜻을 보존한다는 것은 원문의 비유·문장 순서·반복까지 유지한다는 뜻이 아니다. 독자가 알아야 할 대상·조건·결과를 보존하면서 문장을 다시 쓰고, 독자와 무관한 일반 구현 의무는 덜 수 있다. 실제 사용 제약인지 불명확한 내용은 지우지 않고 `needs-decision`으로 남긴다.
- 설명과 근거가 어긋나 보이면 설명을 고치지 않는다. `needs-decision` 메모에 어긋난 설명 위치와 근거 위치만 적는다. 원인이나 결함을 추정해 적지 않는다.

## 경로

- 플러그인 폴더: `${CLAUDE_PLUGIN_ROOT}`
- 프로젝트 루트: `${CLAUDE_PROJECT_DIR}`

값이 변수 이름 그대로 보이면 플러그인 폴더는 이 SKILL.md 의 두 단계 위 폴더, 프로젝트 루트는 세션을 시작한 폴더다. 명령은 프로젝트 루트에서 실행한다. 아래 `<도구>` 는 `python "<플러그인 폴더>/scripts/review_queue.py"` 다(`python` 이 없으면 `python3`).

## 대상 고르기

- 프로젝트 지침과 사용자가 정한 범위를 따른다. 버전 관리 상태(`git status --short` 또는 `p4 opened`)와 그 작업의 메모를 읽는다.
- 목록 폴더는 프로필(`<프로젝트 루트>/.claude/ko-review/profile.md`)의 `queue_dir`, 없으면 `.claude/ko-review/queue` 다.
- 작업을 지정받았으면 `<queue_dir>/<task>.descriptions.json` 을 쓴다. 대기 목록 전체를 요청받았으면 그 폴더의 `*.descriptions.json` 만 찾아 작업별 `taskId` 와 대기 항목 수를 요약하고 대기 항목부터 처리한다. 완료된 목록의 소스까지 읽지 않는다. `closed` 칸이 있는 목록은 닫힌 기록이므로 검토하지 않는다. 보관 폴더(프로필 `queue_archive_dir`)도 찾지 않는다.
- `<도구> pending <task>` 로 현재 내용과 기록을 맞춘다. 설명·근거가 바뀌었거나 위치가 사라진 항목은 이 명령이 대기로 돌린다. `retired` 항목은 작성 쪽이 폐기한 것이므로 출력되지 않고, 검토하지 않는다. `unassignedChanges` 는 파일 단위의 등록 누락 알림이다. 파일 안의 모든 변경 구간이 등록됐다는 보장이 아니다.
- `outOfScopeEntries` 는 프로필 `queue_scope` 밖의 대기 항목이다. 검토하지 않고, 목록 경로와 항목 id 를 완료 보고에 적기만 한다. 지우거나 완료로 기록하지 않는다.
- 항목·위치가 없으면 지정받은 커밋·파일 범위로만 진행한다. 목록이 없다는 이유로 전체 프로젝트 검토나 기록 복원을 시작하지 않는다. 시작 전 변경이나 작성자의 기록이 모호하면 확인할 수 있는 항목만 진행하고 남은 범위를 알린다.

## 읽기와 교정

1. 항목의 `selector`로 실제 설명을 읽는다. `pending` 출력의 `lines`(설명의 시작·끝 줄)로 그 구간과 앞뒤 몇 줄만 읽고, 파일 전체를 열지 않는다. 같은 설정의 빈 값·예외 설명처럼 뜻을 이해하는 데 필요한 줄이 선택 밖에 있으면 읽어서 판단에 쓴다. selector는 고치지 않는다. `evidence`는 위 "역할"의 범위에서만 읽는다.
   - 선택 밖 줄까지 고쳐야 뜻이 맞으면 선택 안만 교정하고, 결과 메모에 선택 밖 위치를 적는다. 위치는 작성 쪽이 고친다.
   - `locationError`가 있는 항목은 `begin`하지 않고 완료 보고에 목록 경로와 항목 id만 적는다.
2. 고치기 전에 `<도구> begin <task> --id <id>` 로 token 과 스냅샷을 받는다. `--reviewer` 를 생략하면 프로필 `reviewer` 값이 검토자로 기록된다. 프로필에 값이 없으면 `--reviewer <자기 이름>` 을 붙인다.
3. 검토를 시작할 때 `polish/SKILL.md`와 항목 `kind`에 맞는 참고 파일을 세션에 한 번 읽는다. `comment`·`data-comment`는 `reference/editor-comments.md`(프로필 `engine`이 `unreal`이면 `reference/unreal.md`도), manual인 `doc`은 `reference/manual.md`다. `reference/word-choice.md`는 낱말 판단이 막힐 때만 읽고, 이 밖의 참고 파일은 없다. 항목마다 다시 읽지 않는다. 원뜻이 분명한 부분은 직접 교정한다. 적용 조건, 부정, 대상 범위, 횟수, 단위, 기본값, 수명, 실제 부작용·실패 처리를 보존한다. `polish`와 참고 파일에서 현재 구현으로 동작을 다시 판단하는 절차는 따르지 않는다. 식별자, 일반 문자열, 메타데이터, 실행 로직, 설정 파일의 키와 생성 파일은 고치지 않는다. `doc_check.py` 등 보조 검사는 사용자·프로젝트의 검사 권한이 허용할 때만 실행한다.
4. 설명과 근거가 어긋나 보이거나 원래 뜻을 알 수 없으면 설명을 고치지 않고 `needs-decision` 으로 기록한다. 메모에는 어긋난 설명 위치와 근거 위치(파일·anchor)만 적는다. 설명에 맞추려고 코드를 바꾸지 않는다.
5. 고쳤으면 `<도구> snapshot <task> --id <id>` 를 한 번 실행한다. 출력의 `descriptionText`로 최종 설명을 원문과 나란히 보지 않고 다시 읽는다. 파일을 다시 열지 않는다. `polish`의 "교정 완료 판단"을 모두 만족하는지 본다. 툴팁이면 항목 이름과 본문만으로 설정 대상·적용 조건·빈 값의 결과를 알 수 있어야 한다. 검색된 단어만 사라졌거나 짧다는 이유로 통과시키지 않는다.

## 결과 기록

- `<도구> finish <task> --id <id> --token <token> --note "결과"` 로 기록한다. 판단이 필요하면 `--status needs-decision` 을 붙인다.
- 설명을 직접 고쳤으면 5에서 받은 `snapshot` 출력의 `description.sha256` 을 `--description-hash` 로 넘긴다. 5 뒤에 다시 고쳤으면 `snapshot` 을 다시 실행한다. 해시 계산은 품질 검토를 대신하지 않는다.
- 결과 메모에는 어떤 모호함을 없앴는지 짧게 쓴다. 유지한 경우에도 역할·빈 값·적용 범위 등 실제 판단 근거를 쓴다. “뜻이 분명하므로 유지했다”만으로 끝내지 않는다. `reviewed`는 이번 항목의 검토 기록이며 파일 전체나 이후 요청의 품질을 보증하지 않는다. 사용자가 기존 문장의 재교정을 요청하면 `polish`로 새 범위를 다루고 닫힌 기록은 다시 열지 않는다.
- 검토 중에 근거가 바뀌었거나 최종 설명 해시가 다르면 도구가 완료 기록을 거절한다. 현재 내용을 다시 읽고 `begin` 부터 한 번 다시 한다. 또 거절되면 그 항목을 남기고 오류 메시지를 완료 보고에 적는다. 다른 작업자의 변경을 되돌리지 않는다.
- 자기가 고친 내용은 최종 내용으로 `finish` 한다. 작성 쪽 방식(`register`)으로 다시 등록해 자기 수정이 계속 대기에 남게 만들지 않는다. 이후 작성 쪽이 설명·근거를 또 고치면 다음 `pending` 에서 다시 대기가 된다.
- 목록 파일(`*.descriptions.json`)을 직접 고치지 않는다. 도구의 소스를 읽어 거절을 우회하지 않는다. 도구가 거절하면 오류 메시지를 그대로 보고한다. 도구 오류를 성공으로 바꿔 적지 않는다.

## 지키는 것

- 빌드·테스트·lint·별도 코드 검사·테스트 코드 추가는 하지 않는다. 프로필 `check_runs` 가 `agent` 이고 사용자 요청 범위에 있을 때만 예외다.
- 커밋·이슈 댓글 같은 외부 게시는 프로젝트 지침의 승인 절차를 따른다.
- 완료 보고에는 처리한 작업과 항목, 대표 교정 예, 판단이 필요한 항목, 실제로 실행한 검사를 적는다. 요청 범위의 문서와 작업 메모를 갱신한다.
