# 설명 변경 부분 검토 (검토 쪽)

이 스킬 파일과 요청서만 읽고 교정문을 결과 파일 하나에 쓴다. 문장 기준과 필요한 근거는 요청서에 들어 있다. 도구를 실행하지 않으므로 Python 이 없어도 된다.

## 역할

대기 항목의 주석·문서·설정 설명을 자연스러운 한국어로 교정한다. 코드 기능 검수, 버그 판단, 동작 추정은 하지 않는다.

- 근거 구현(`evidence`)은 교정한 문장이 원래 뜻을 바꾸지 않았는지 확인하는 데만 읽는다. 적용 조건, 부정, 횟수, 단위, 기본값, 실패 조건이 원문과 같은지 본다.
- 재현하지 않은 동작이나 한계를 설명에 새로 쓰지 않는다. 원문에 없는 조건·제한·이유를 더하지 않는다.
- 뜻을 보존한다는 것은 원문의 비유·문장 순서·반복까지 유지한다는 뜻이 아니다. 독자가 알아야 할 대상·조건·결과를 보존하면서 문장을 다시 쓰고, 독자와 무관한 일반 구현 의무는 덜 수 있다. 실제 사용 제약인지 불명확한 내용은 지우지 않고 `needs-decision`으로 남긴다.
- 설명과 근거가 어긋나 보이면 설명을 고치지 않는다. `needs-decision` 메모에 어긋난 설명 위치와 근거 위치만 적는다. 원인이나 결함을 추정해 적지 않는다.

## 경로

- 목록 폴더는 프로필 `queue_dir`, 없으면 `.claude/ko-review/queue` 다. 요청서 경로를 받지 못했을 때만 프로필(`.claude/ko-review/profile.md`)에서 이 값을 확인한다.
- 요청서는 `<queue_dir>/<task>.request.md` 다.
- 결과 파일 경로는 요청서에 적혀 있다. 기본 위치는 `<queue_dir>/<task>.result.json` 이다.

## 대상 고르기

- 요청서 경로를 받으면 그 파일을 읽는다.
- 작업 ID 만 받으면 목록 폴더의 `<task>.request.md` 를 연다.
- 대기 전체를 요청받으면 목록 폴더의 `*.request.md` 파일 이름만 찾아 차례로 처리한다.
- 목록 파일(`*.descriptions.json`), 소스 파일, `polish` 스킬 파일과 참고 파일, `review_queue.py`, 프로젝트 지침, 버전 관리 상태는 읽지 않는다. 저장소를 훑는 검색을 하지 않는다.

## 읽기와 교정

1. 요청서의 항목마다 종류·위치·등록 이유·고칠 글·앞뒤 문맥·근거 구간을 읽는다. 문장 기준과 프로젝트 낱말 목록의 확정 금지 표현(`banned`, `banned_patterns`)도 요청서에 들어 있는 것을 쓴다.
2. 원뜻이 분명한 부분을 교정한다. 적용 조건, 부정, 대상 범위, 횟수, 단위, 기본값, 수명, 부작용, 실패 처리를 보존한다. 요청서의 문장 기준 가운데 현재 구현으로 동작을 다시 판단하는 절차는 따르지 않는다. 근거는 교정이 원래 뜻을 바꾸지 않았는지 확인하는 데만 쓴다.
3. `text` 에는 항목의 "고칠 글" 전체를 대신할 글을 쓴다. 설명 밖의 줄과 글자(코드, 설정 키, 들여쓰기, 주석 기호)는 그대로 둔다. 줄 수는 바뀌어도 된다. 고칠 것이 없으면 원문 그대로 둔다.
4. 설명과 근거가 어긋나 보이거나 원래 뜻을 알 수 없을 때, 사용 제약인지 불명확한 내용을 지워야 할 때는 `needs-decision` 으로 남긴다. 이때 `text` 는 원문 그대로 두고 `note` 에 어긋난 설명 위치와 근거 위치만 적는다.
5. 최종 교정문을 원문과 나란히 보지 않고 다시 읽는다. 요청서의 "교정 완료 판단"을 모두 만족하는지 본다.

## 결과 기록

요청서에 적힌 결과 파일 경로에 다음 형식으로 쓴다. 요청서의 모든 항목을 넣고, `status` 는 `reviewed` 또는 `needs-decision` 으로 쓴다. 결과 파일은 작성 쪽이 `items` 가 빈 형식으로 미리 만들어 둔다. 파일을 지우거나 새로 만들지 않고 내용만 바꾼다. Windows 의 Codex 샌드박스가 새로 만든 파일은 작성 쪽 계정이 읽지 못할 수 있다.

`{"requestId": "<요청 ID>", "items": [{"id": "...", "status": "reviewed", "text": "...", "note": "..."}]}`

- `requestId` 는 요청서의 요청 ID 를 그대로 쓴다.
- `note` 는 한 줄로 쓴다. 어떤 모호함을 없앴는지 적고, 그대로 뒀으면 실제 판단 근거를 쓴다. "뜻이 분명하므로 유지했다"만으로 끝내지 않는다. `needs-decision` 항목은 위 "읽기와 교정"의 메모 규칙을 따른다.
- 소스 파일을 직접 고치지 않는다. 결과 파일 밖의 파일을 만들거나 고치지 않는다.
- 목록 파일과 도구를 직접 다루지 않는다. `pending` 은 작성 쪽이 쓰고, `begin`·`snapshot`·`finish` 는 사람이 검토 결과를 직접 기록할 때만 쓴다.

## 지키는 것

- 빌드·테스트·lint·별도 코드 검사·테스트 코드 추가는 하지 않는다. 프로필 `check_runs` 가 `agent` 이고 사용자 요청 범위에 있을 때만 예외다.
- 커밋·이슈 댓글 같은 외부 게시는 프로젝트 지침의 승인 절차를 따른다.
- 완료 보고에는 처리한 항목 수, 대표 교정 예, `needs-decision` 항목을 적는다. 교정문은 작성 쪽이 `apply` 로 반영한다고 알린다.
