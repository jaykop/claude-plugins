# 기능 문서와 설명 변경 목록 반영

프로젝트 지침과 사용자 요청을 우선한다. 구현 뒤 현재 사용법을 관련 문서에 반영하고, 바꾼 설명을 다른 AI 가 부분 검토할 수 있도록 남긴다. 이 절차는 빌드·테스트·별도 코드 검사를 실행할 권한을 주지 않는다.

프로필은 `<프로젝트 루트>/.claude/workflow/profile.md` 다. 쓰는 칸: `docs`(index·manual·devlog·plan·templates), `tracker`·`tracker_public`, `status_labels`, `threads_dir`, `description_review`, `doc_writer`. 프로필이 없으면 프로젝트 지침과 `docs/` 구성을 읽어 문서 위치를 확인받는다.

`doc_writer` 가 `codex` 면 이 스킬을 쓰는 쪽(구현한 쪽)은 manual·devlog·plan 의 문장을 직접 쓰지 않는다. 2 에서 문서 지시서를 쓰고, 문서를 쓰는 쪽이 `doc-draft` 로 쓴 결과를 5 에서 대조한다. 문장 품질은 문서를 쓰는 쪽에 맡기고, 사실의 정확성은 대화와 구현을 아는 쪽이 지키기 위해서다. 비어 있거나 `claude` 면 이 스킬을 쓰는 쪽이 직접 쓰고 5 를 건너뛴다.

## 1. 영향과 작업 상태

연결 이슈, 이번 구현 범위, 사용자 확인 결과와 남은 작업을 구분한다. 작업 상태는 이슈, 현재 사용법·제한은 manual, 중요한 결정 이유는 devlog 에 둔다. 이슈 게시는 초안을 준비하고 사용자 확인을 받는다. 개인 시행착오·로컬 설정·세션 메모는 인계 메모(`threads_dir`)에 둔다.

공개 API·UI·설정·실행 방법·기존 데이터 처리 방법이 바뀌면 같은 작업에서 관련 manual 을 갱신한다. 전체 상태 요약 문서를 만들지 않는다. 내부 구현 변경도 기존 설명에 영향을 주는지 판단한다.

## 2. 관련 문서 갱신

고치기 전에 해당 카테고리의 실제 템플릿(`docs.templates`)을 읽는다. 이 스킬에 템플릿을 복사해 두지 않는다.

- 현재 사용법: manual 템플릿
- 변경·결정·진단: devlog 템플릿
- 이슈의 설계안: plan 템플릿. 정하지 않은 사항을 현재 사양으로 쓰지 않는다

같은 주제의 기존 문서부터 갱신하고, 새 문서나 경로 변경이 있으면 문서 목록(`docs.index`)과 관련 링크도 반영한다. 단순 오탈자마다 devlog 를 추가하지 않는다. 과거 기록의 당시 판단과 사용자 확인 범위는 보존하고, 후속 변경은 링크로 연결한다.

### `doc_writer: codex` 일 때 — 문서 지시서

문서를 고치는 대신 `<threads_dir>/<작업 ID>.docbrief.md` 를 쓴다. 양식은 `<플러그인 폴더>/shared/docbrief-template.md` 다(플러그인 폴더는 이 SKILL.md 의 두 단계 위 폴더).

- 무엇을 어느 문서에 쓸지는 위 규칙대로 정하고 "쓸 문서" 표에 적는다. 템플릿 경로도 함께 적는다.
- 문서에 들어갈 사실을 빠짐없이 적되 문장으로 쓰지 않는다. 사실마다 근거(코드 경로:줄, 커밋, 이슈, 사용자 확인 기록)를 붙인다. 쓰는 쪽은 이 대화를 보지 못하므로, 대화에서만 정해진 결정·이유·사용자 확인은 출처(날짜와 누가 말했는지)까지 적는다.
- 정하지 않은 것은 "미확정 사항"에, 확인하지 않은 빌드·실행은 "확인 상태"의 확인하지 않은 범위에 둔다.
- 오탈자·링크 경로처럼 문장을 새로 쓰지 않는 한 줄 수정은 지시서 없이 직접 고쳐도 된다.
- 넘기는 때와 방법(호출 명령, 한 번에 넘길 범위)은 프로젝트 지침을 따른다. 지침이 없으면 사용자에게 지시서 경로를 알려 주고 넘기는 일은 사용자에게 맡긴다.

## 3. 문장과 기술 설명 교정

`doc_writer: codex` 면 이 절을 건너뛴다. 문장 교정은 문서를 쓰는 쪽이 하고, 사실 대조는 5 에서 한다.

ko-review 플러그인이 설치돼 있으면 그 `polish` 스킬의 기준으로, 작성·수정한 문단과 인접 항목을 읽는다. 자연스러운 한국어인지, 설정 대상·조건·단위·결과·제한이 실제 구현과 맞는지 대조한다. 뜻이 분명한 교정은 직접 한다. 알 수 없는 동작은 추정해 쓰지 않고 남은 의문으로 보고한다.

## 4. 설명 변경 목록 갱신

프로필 `description_review` 가 true 면 ko-review `record` 스킬을 따른다. 대상은 ko-review 프로필 `queue_scope` 에 맞는 파일이다(비었으면 모든 설명 파일). 범위 밖 문서(devlog·plan·문서 목록 등)는 항목으로 등록하지 않고 `no-impact` 로 남긴다. 문서화만 요청받은 작업도 고치기 전에 `start` 나 `scope` 로 파일 상태를 기록하고, 끝나면 `capture` → `register` / `no-impact` 로 남긴다.

- 로직 변경으로 영향을 받는 미수정 설명도 등록한다.
- 이후 설명을 또 바꾸면 같은 id 를 다시 등록해 대기로 돌린다. 검토하는 쪽이 목록을 고치는 중이면 동시에 고치지 않고 현재 내용을 먼저 읽는다.
- 이 기록은 후속 질문이나 사용자 빌드 확인 전에도 남긴다. 다른 AI 를 자동으로 부르거나 메시지를 보내지 않는다.
- `doc_writer: codex` 면 지시서로 넘기는 문서는 이 목록에 등록하지 않는다. 쓰는 쪽이 쓰고 구현한 쪽이 5 에서 대조하므로, 같은 문서를 교정 목록에 다시 넣으면 쓴 쪽이 자기 글을 교정하게 된다. 프로젝트가 ko-review 프로필 `queue_scope` 에서 그 문서 폴더를 빼 두면 등록 시도가 거절된다.

## 5. 쓴 결과 대조 (`doc_writer: codex`)

쓰는 쪽이 지시서 상태를 "작성됨" 또는 "재작성됨"으로 바꾼 뒤에 한다.

1. "쓸 문서" 의 diff 와 지시서의 "작성 결과"를 읽는다. 표에 없는 파일이나 절이 바뀌었으면 그 구간을 사용자에게 보여 주고 되돌릴지 묻는다.
2. 문단마다 지시서의 사실·결정·확인 상태·미확정 사항과, 필요하면 근거 코드와 대조한다. 보는 것은 사실이다: 지시서와 다른 내용, 지시서에 없는 내용(추정한 동작·한계·수치 포함), 빠진 사실, 미확정을 확정처럼 쓴 곳, 확인하지 않은 결과를 확인한 것처럼 쓴 곳.
3. **문장은 고치지 않는다.** 문제는 "대조 결과" 표에 위치·문제·맞는 사실로 적는다. 맞는 사실이 지시서에 없었으면 지시서의 사실 표에 더하고 그 ID 를 적는다. 사용자 판단이 필요한 것은 처리를 "사용자 확인"으로 둔다.
4. "재작성" 행이 있으면 상태를 "재작성 대기"로 바꾸고 다시 넘긴다(넘기는 방법은 2 와 같다). 재작성은 한 번만 넘긴다. 재작성 뒤 대조에서 남은 문제는 다시 넘기지 않고 사용자에게 보여 준다.
5. 문제가 없으면 상태를 "대조 완료"로 바꾼다. 문체·용어에 대한 의견은 고치지 않고 보고에만 적는다.

## 완료 보고

관련 문서와 목록 경로(`doc_writer: codex` 면 지시서 경로와 상태), 실제 교정 범위, 판단이 필요한 항목, 사용자 확인 결과와 실행하지 않은 검사를 간결하게 보고한다. 이슈가 있으면 결과 기록 초안과 문서 링크를 준비하고, 게시 여부는 사용자에게 묻는다. 구현만 끝나고 사용자 확인 전이면 `status_labels.needs_verification` 라벨을 제안한다.
