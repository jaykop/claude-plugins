# 기능 문서와 설명 변경 목록 반영

프로젝트 지침과 사용자 요청을 우선한다. 구현 뒤 현재 사용법을 관련 문서에 반영하고, 바꾼 설명을 다른 AI 가 부분 검토할 수 있도록 남긴다. 이 절차는 빌드·테스트·별도 코드 검사를 실행할 권한을 주지 않는다.

프로필은 `<프로젝트 루트>/.claude/workflow/profile.md` 다. 쓰는 칸: `docs`(index·manual·devlog·plan·templates), `tracker`·`tracker_public`, `status_labels`, `threads_dir`, `description_review`. 프로필이 없으면 프로젝트 지침과 `docs/` 구성을 읽어 문서 위치를 확인받는다.

## 1. 영향과 작업 상태

연결 이슈, 이번 구현 범위, 사용자 확인 결과와 남은 작업을 구분한다. 작업 상태는 이슈, 현재 사용법·제한은 manual, 중요한 결정 이유는 devlog 에 둔다. 이슈 게시는 초안을 준비하고 사용자 확인을 받는다. 개인 시행착오·로컬 설정·세션 메모는 인계 메모(`threads_dir`)에 둔다.

공개 API·UI·설정·실행 방법·기존 데이터 처리 방법이 바뀌면 같은 작업에서 관련 manual 을 갱신한다. 전체 상태 요약 문서를 만들지 않는다. 내부 구현 변경도 기존 설명에 영향을 주는지 판단한다.

## 2. 관련 문서 갱신

고치기 전에 해당 카테고리의 실제 템플릿(`docs.templates`)을 읽는다. 이 스킬에 템플릿을 복사해 두지 않는다.

- 현재 사용법: manual 템플릿
- 변경·결정·진단: devlog 템플릿
- 이슈의 설계안: plan 템플릿. 정하지 않은 사항을 현재 사양으로 쓰지 않는다

같은 주제의 기존 문서부터 갱신하고, 새 문서나 경로 변경이 있으면 문서 목록(`docs.index`)과 관련 링크도 반영한다. 단순 오탈자마다 devlog 를 추가하지 않는다. 과거 기록의 당시 판단과 사용자 확인 범위는 보존하고, 후속 변경은 링크로 연결한다.

## 3. 문장과 기술 설명 교정

ko-review 플러그인이 설치돼 있으면 그 `polish` 스킬의 기준으로, 작성·수정한 문단과 인접 항목을 읽는다. 자연스러운 한국어인지, 설정 대상·조건·단위·결과·제한이 실제 구현과 맞는지 대조한다. 뜻이 분명한 교정은 직접 한다. 알 수 없는 동작은 추정해 쓰지 않고 남은 의문으로 보고한다.

## 4. 설명 변경 목록 갱신

프로필 `description_review` 가 true 면 ko-review `record` 스킬을 따른다. 문서화만 요청받은 작업도 고치기 전에 `start` 나 `scope` 로 파일 상태를 기록하고, 끝나면 `capture` → `register` / `no-impact` 로 남긴다.

- 로직 변경으로 영향을 받는 미수정 설명도 등록한다.
- 이후 설명을 또 바꾸면 같은 id 를 다시 등록해 대기로 돌린다. 검토하는 쪽이 목록을 고치는 중이면 동시에 고치지 않고 현재 내용을 먼저 읽는다.
- 이 기록은 후속 질문이나 사용자 빌드 확인 전에도 남긴다. 다른 AI 를 자동으로 부르거나 메시지를 보내지 않는다.

## 완료 보고

관련 문서와 목록 경로, 실제 교정 범위, 판단이 필요한 항목, 사용자 확인 결과와 실행하지 않은 검사를 간결하게 보고한다. 이슈가 있으면 결과 기록 초안과 문서 링크를 준비하고, 게시 여부는 사용자에게 묻는다. 구현만 끝나고 사용자 확인 전이면 `status_labels.needs_verification` 라벨을 제안한다.
